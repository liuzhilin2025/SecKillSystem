## 二、消息可能丢失的三个环节

```
① 生产端 → Broker      ② Broker 内部存储       ③ Broker → 消费端
   （网络抖动/宕机）        （未持久化/磁盘故障）      （消费失败未重试）
   解决：Confirm + 重试    解决：持久化 + 镜像队列    解决：手动 ACK + DLX + 重试
   + 失败补偿表
```

本章聚焦 **① 生产端**。

## 三、Spring Retry 重试发送

### 启用

```java
@EnableRetry
@SpringBootApplication
public class FlashSaleApplication { ... }
```

### 使用

```java
@Retryable(
    retryFor = {AmqpException.class, Exception.class},
    maxAttempts = 3,
    backoff = @Backoff(delay = 200, multiplier = 2)   // 200ms、400ms、800ms 退避
)
public void sendSeckillMessage(SeckillMessage msg) {
    rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, msg);
}

@Recover
public void recover(Exception e, SeckillMessage msg) {
    // 重试全部失败 → 落库登记，交给定时任务补偿
    mqFailRecordMapper.insert(MqFailRecord.from(msg, e.getMessage()));
    log.error("秒杀消息发送失败，已登记补偿, msg={}", msg, e);
}
```

### 参数说明

| 参数 | 含义 |
|---|---|
| `maxAttempts` | 总尝试次数（含首次），注意不是"重试次数" |
| `backoff.delay` | 首次重试等待 |
| `backoff.multiplier` | 退避倍数，避免同一时刻疯狂重试 |
| `@Recover` | 所有重试耗尽后的兜底方法，**参数必须包含异常且返回类型一致** |

## 四、失败补偿表 + 定时补偿

### 表结构建议

```sql
CREATE TABLE t_mq_fail_record (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_type     VARCHAR(32)  NOT NULL COMMENT '业务类型，如 SECKILL_ORDER',
    msg_id       VARCHAR(64)  NOT NULL COMMENT '业务唯一ID（订单号）',
    payload      TEXT         NOT NULL COMMENT '消息体 JSON',
    status       TINYINT      NOT NULL DEFAULT 0 COMMENT '0待补偿 1补偿成功 2补偿失败',
    retry_count  INT          NOT NULL DEFAULT 0,
    error_msg    VARCHAR(512),
    next_retry_at DATETIME    NOT NULL COMMENT '下次补偿时间',
    created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_msg_id (msg_id)
) COMMENT 'MQ 发送失败补偿表';
```

### 补偿任务

```java
@Scheduled(fixedDelay = 30_000)   // 每 30 秒扫一次
public void compensate() {
    List<MqFailRecord> list = mapper.selectPending(100);  // 限制批量大小
    for (MqFailRecord r : list) {
        try {
            rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, r.getPayload());
            mapper.markSuccess(r.getId());
        } catch (Exception e) {
            // 指数退避更新 next_retry_at，超过上限则告警并置为失败
            mapper.markRetry(r.getId(), e.getMessage());
        }
    }
}
```

### 关键设计点

| 关注点 | 做法 |
|---|---|
| 幂等 | 补偿重发可能造成**重复投递**，消费端必须按 `msg_id` 幂等 |
| 重试上限 | 超过 N 次（如 10 次）不再重试，转为人工/告警处理 |
| 退避 | `next_retry_at` 指数增长，避免无效重试打爆 MQ |
| 消费失败 | 超限后**回补 Redis 库存**，保证用户可再次抢购 |
| 幂等键 | `msg_id` 用业务订单号，天然唯一 |
| 可观测 | 补偿表积压数量接入监控告警 |

## 六、验收标准

| 指标 | 要求 |
|---|---|
| 消息不丢 | 停 MQ 期间产生的秒杀请求，恢复后全部成功落库 |
| 无重复订单 | 补偿重发 + 重复投递场景下订单数正确 |
| 补偿可收敛 | 补偿表最终趋于清空；异常数据有告警 |
| 数据一致 | Redis 扣减数 = DB 订单数 + 补偿中数量 |

## 七、常见坑

- `@Retryable` 与 `@Transactional` 混用，事务未提交就重试导致脏数据
- `@Recover` 方法签名不匹配（参数/返回类型），Spring 无法识别 → 兜底不生效
- **同类内部方法调用 `@Retryable` 方法**，AOP 不生效（需通过代理调用或自注入）
- 补偿任务无重试上限 → 死信消息永久循环重发
- 补偿表无唯一索引 → 重复登记，重复补偿
- 只做补偿不做告警 → 失败被静默吞掉，问题发现不了
- 忘记"补偿超限后回补库存" → 用户扣了额度却拿不到商品

## 八、面试追问

### 当时卡在哪

**卡点一：发送失败只是打了一行日志。**

最早的 `send()` 是 `try { convertAndSend(...) } catch (AmqpException e) { log.error(...); return false; }`。看着挺稳妥，实际上——**日志打完就没了**。库存已经在 Redis 扣掉，订单却永远不会有，这笔账谁也不知道。

**卡点二：加了 `@Retryable`，重试却没发生。**

把 catch 去掉、换成 `@Retryable(maxAttempts = 3)`，以为万事大吉。结果在同一个类里用 `this.send(...)` 调了一下，重试一点动静都没有。后来才知道：**`@Retryable` 靠 AOP 代理生效，自己调自己，代理被绕过去了。**

**卡点三：`@Recover` 写对了方法名，却没被调用。**

兜底方法签名写成 `recover(Exception e, SeckillOrderMqDTO message)`，看起来很像，实际不匹配——`@Recover` 的第一个参数必须和 `@Retryable(retryFor = ...)` 里声明的异常**完全一致**，写成父类 `Exception` 就匹配不上，兜底静默失效。

**卡点四：补偿记录被重复登记。**

第一次失败插一条，第二次失败又插一条，最后同一笔订单在补偿表里躺着好几行，定时任务挨个重发，同一张订单被提交多次。

**卡点五：`setStatus` 写在了 mapper 后面，差点以为状态更新了。**

```java
sendCompensationMapper.updateStatusByOrderNo(orderNo, MANUAL_PENDING);
existCompensation.setStatus(MANUAL_PENDING);   // ← 只改了内存对象
```

第二行改的是刚从数据库查出来的那个 POJO，方法一结束就被 GC 了，**数据库里一个字都没变**。更危险的是它看起来"像"已经更新了，后面维护的人很容易把上面那行真正的 UPDATE 删掉。

### 为什么最后引入了这些技术

**`@Retryable` + `@Recover`**，引入它是为了：

- 不是让失败消失，而是让失败**多试几次**；
- 不是把异常吞掉，而是把异常**收进一个有人负责的地方**；
- 不是保证"一定成功"，而是保证"失败一定留下痕迹"。

**补偿表**，引入它是为了：

- 不是多建一张表，而是给"发不出去的消息"一个**落脚点**；
- 不是把问题藏起来，而是把问题**变成一条可查询、可重发、可统计的记录**；
- 不是替代 MQ 的重试，而是接住 MQ 重试**接不住的那部分**。

**指数退避 + 重试上限**，引入它是为了：

- 不是让重试更慢，而是让重试**更聪明**；
- 不是放弃消息，而是承认"有些问题不是重试能解决的"；
- 不是给系统偷懒的理由，而是给人工介入留一个**明确的入口**。

**宁可让一条消息进人工队列，也不要让它在系统里无限循环。**

### 面试追问（附参考答案）

**Q1：MQ 消息可能在哪几个环节丢失？分别怎么防？**

A：三个环节，三道防线：

| 环节 | 丢失原因 | 防护 |
|---|---|---|
| 生产者 → Broker | 网络抖动、Broker 未确认 | `publisher-confirm`（到达交换机）+ `publisher-returns`（路由到队列）+ 失败落补偿表 |
| Broker 内部 | 消息在内存里没落盘就宕机 | 交换机/队列 `durable=true`、消息 `deliveryMode=PERSISTENT`、镜像/仲裁队列 |
| Broker → 消费者 | 消费者拿到就 ACK，处理时崩溃 | 手动 ACK（处理成功才 `basicAck`）+ 重试 + 死信队列 |

口诀：**发得出、存得住、收得下。**

要注意：**三道防线只能做到"至少一次"，做不到"恰好一次"**。所以第四道防线是消费端幂等（见 Q4）。

**Q2：RabbitMQ 的 Confirm 机制和事务机制有什么区别？为什么推荐 Confirm？**

A：
- **事务机制**（`txSelect` / `txCommit` / `txRollback`）：同步阻塞。每次 `commit` 都要等 Broker 确认，吞吐会掉一个数量级，而且它是**强阻塞**的，一个慢确认能拖住整个发送线程。
- **Confirm 机制**：异步回调。`convertAndSend` 立刻返回，Broker 处理完通过 `ConfirmCallback` 异步告诉你成功还是失败（`ack` / `nack`）。可以批量确认，吞吐高得多。

为什么推荐 Confirm：
1. 性能差一个数量级；
2. 事务机制只保证"Broker 收到了"，不保证"路由到了队列"——要覆盖路由失败还得配 `mandatory` + `ReturnCallback`；
3. Confirm 是异步的，天然不阻塞业务线程。

项目里配的是 `publisher-confirm-type: correlated` + `publisher-returns: true` + `template.mandatory: true`，三件套齐了才能覆盖"到交换机"和"到队列"两段。

**Q3：补偿表和本地消息表（事务消息）各自的优劣？**

A：
- **本地消息表**：业务数据和消息记录写在**同一个本地事务**里，保证"业务成功 ⇒ 消息一定被记录"；再由定时任务扫描未发送的记录去投递。
  - 优点：不依赖 MQ 的事务能力，任何 MQ 都能用，一致性最强；
  - 缺点：**消息表和业务表耦合在同一个库**，等于把 MQ 的可靠性责任揽到自己身上；定时任务有延迟。
- **补偿表**（项目用的）：消息**已经尝试发送但失败**之后才登记，属于"事后补救"。
  - 优点：实现简单，只在失败路径上写库，正常流程零开销；
  - 缺点：**只能兜住"发送失败"，兜不住"业务提交了但压根没发"**；依赖失败回调的可靠性。

选择逻辑：**要求"绝不漏发"用本地消息表；要求"失败能重来"用补偿表。** 秒杀场景里，"预扣成功但消息没发出去"已经被回补逻辑兜住了，所以补偿表够用。

**Q4：至少一次投递为什么要求消费端幂等？**

A：因为"至少一次"意味着**同一条消息可能被投递多次**，触发场景很常见：
- 消费者处理完了，但 `basicAck` 在网络中丢了 → Broker 认为没消费，重新投递；
- 消费者处理到一半崩溃，连接断开 → 消息重回队列；
- 生产端 Confirm 超时重发，Broker 里其实已经有了一条。

不幂等的后果：订单重复创建、库存重复扣减、用户重复扣款。

实现幂等的三种常见手段：
1. **唯一索引**（项目用的）：`order_no` 唯一，重复插入抛 `DuplicateKeyException`，捕获后当成功处理；
2. **状态机**：只允许 `待支付 → 已支付`，重复消息进来发现状态已经是终态，直接跳过；
3. **去重表 / Redis 标记**：处理前先 `SETNX messageId`，已存在就丢弃。

**最可靠的是唯一索引**——它不依赖代码正确性，依赖数据库约束。

**Q5：补偿重试次数上限怎么定？超限后怎么处理？**

A：上限不是拍一个数，而是按**退避总时长**倒推。

项目里的策略是：初始 10 秒，每次翻倍（10 → 20 → 40 → 80 → 160），封顶 300 秒，最多 5 次。算下来大约 **5 分钟内**能覆盖掉绝大多数瞬时故障（网络抖动、Broker 重启、数据库短暂不可用）。

超限后的处理原则：**不要静默丢弃，要转人工**。
- 状态置为 `MANUAL_PENDING`，写清楚最后一次失败原因；
- 打 `ERROR` 日志 + 接告警（钉钉/企微/邮件）；
- 提供人工重发入口（管理后台或脚本）。

关键认知：**重试上限不是"放弃"，而是"把自动放弃换成人工接手"。**

**Q6：如果补偿任务本身挂了怎么办？**

A：四个层面：

1. **多实例 + 分布式锁**：定时任务在多副本部署时会重复执行，用 Redis 锁（`SETNX` + TTL）保证同一时刻只有一个实例在跑。
2. **任务自身可观测**：记录"上次执行时间""本轮处理条数""失败条数"，超过阈值告警。**最怕的是任务静默停止，没人发现。**
3. **幂等 + 可重入**：任务中途崩溃，下次启动要能从断点继续，不能因为"处理到一半"就卡死。
4. **兜底监控**：单独监控"补偿表里 `status=待重试` 且 `next_retry_time` 已过期超过 N 分钟"的记录数，数量上涨就说明补偿链路出问题了。

一句话：**补偿机制本身也需要被补偿——监控就是它的补偿。**
