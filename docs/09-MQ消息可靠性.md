## 二、消息可能丢失的三个环节

```
① 生产端 → Broker      ② Broker 内部存储       ③ Broker → 消费端
   （网络抖动/宕机）        （未持久化/磁盘故障）      （消费失败未重试）
   解决：Confirm + 重试    解决：持久化 + 镜像队列    解决：手动 ACK + DLX + 重试
   + 失败补偿表
```

本章聚焦 **① 生产端**。

## 三、Spring Retry 重试发送

### 启用

```java
@EnableRetry
@SpringBootApplication
public class FlashSaleApplication { ... }
```

### 使用

```java
@Retryable(
    retryFor = {AmqpException.class, Exception.class},
    maxAttempts = 3,
    backoff = @Backoff(delay = 200, multiplier = 2)   // 200ms、400ms、800ms 退避
)
public void sendSeckillMessage(SeckillMessage msg) {
    rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, msg);
}

@Recover
public void recover(Exception e, SeckillMessage msg) {
    // 重试全部失败 → 落库登记，交给定时任务补偿
    mqFailRecordMapper.insert(MqFailRecord.from(msg, e.getMessage()));
    log.error("秒杀消息发送失败，已登记补偿, msg={}", msg, e);
}
```

### 参数说明

| 参数 | 含义 |
|---|---|
| `maxAttempts` | 总尝试次数（含首次），注意不是"重试次数" |
| `backoff.delay` | 首次重试等待 |
| `backoff.multiplier` | 退避倍数，避免同一时刻疯狂重试 |
| `@Recover` | 所有重试耗尽后的兜底方法，**参数必须包含异常且返回类型一致** |

## 四、失败补偿表 + 定时补偿

### 表结构建议

```sql
CREATE TABLE t_mq_fail_record (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    biz_type     VARCHAR(32)  NOT NULL COMMENT '业务类型，如 SECKILL_ORDER',
    msg_id       VARCHAR(64)  NOT NULL COMMENT '业务唯一ID（订单号）',
    payload      TEXT         NOT NULL COMMENT '消息体 JSON',
    status       TINYINT      NOT NULL DEFAULT 0 COMMENT '0待补偿 1补偿成功 2补偿失败',
    retry_count  INT          NOT NULL DEFAULT 0,
    error_msg    VARCHAR(512),
    next_retry_at DATETIME    NOT NULL COMMENT '下次补偿时间',
    created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_msg_id (msg_id)
) COMMENT 'MQ 发送失败补偿表';
```

### 补偿任务

```java
@Scheduled(fixedDelay = 30_000)   // 每 30 秒扫一次
public void compensate() {
    List<MqFailRecord> list = mapper.selectPending(100);  // 限制批量大小
    for (MqFailRecord r : list) {
        try {
            rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, r.getPayload());
            mapper.markSuccess(r.getId());
        } catch (Exception e) {
            // 指数退避更新 next_retry_at，超过上限则告警并置为失败
            mapper.markRetry(r.getId(), e.getMessage());
        }
    }
}
```

### 关键设计点

| 关注点 | 做法 |
|---|---|
| 幂等 | 补偿重发可能造成**重复投递**，消费端必须按 `msg_id` 幂等 |
| 重试上限 | 超过 N 次（如 10 次）不再重试，转为人工/告警处理 |
| 退避 | `next_retry_at` 指数增长，避免无效重试打爆 MQ |
| 消费失败 | 超限后**回补 Redis 库存**，保证用户可再次抢购 |
| 幂等键 | `msg_id` 用业务订单号，天然唯一 |
| 可观测 | 补偿表积压数量接入监控告警 |

## 六、验收标准

| 指标 | 要求 |
|---|---|
| 消息不丢 | 停 MQ 期间产生的秒杀请求，恢复后全部成功落库 |
| 无重复订单 | 补偿重发 + 重复投递场景下订单数正确 |
| 补偿可收敛 | 补偿表最终趋于清空；异常数据有告警 |
| 数据一致 | Redis 扣减数 = DB 订单数 + 补偿中数量 |

## 七、常见坑

- `@Retryable` 与 `@Transactional` 混用，事务未提交就重试导致脏数据
- `@Recover` 方法签名不匹配（参数/返回类型），Spring 无法识别 → 兜底不生效
- **同类内部方法调用 `@Retryable` 方法**，AOP 不生效（需通过代理调用或自注入）
- 补偿任务无重试上限 → 死信消息永久循环重发
- 补偿表无唯一索引 → 重复登记，重复补偿
- 只做补偿不做告警 → 失败被静默吞掉，问题发现不了
- 忘记"补偿超限后回补库存" → 用户扣了额度却拿不到商品
