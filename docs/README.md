# 秒杀系统高并发优化实战 · 学习计划总览

> 来源：犬小哈教程专栏《秒杀系统高并发优化实战》 <https://www.quanxiaoha.com/column/10659.html>
> 说明：该专栏正文需订阅解锁，本学习计划是**基于其公开目录与架构演进路线**整理的可执行学习方案，供本项目 `FlashSaleSystem` 落地实践使用。

---

## 一、项目定位

从 0 到 1 渐进式搭建一个能扛住高并发的秒杀系统，采用 **问题驱动 + 压测验证** 的方式推进：
先在朴素实现上把问题"制造"出来（超卖、重复下单、雪崩），再用缓存、MQ、Lua、限流等手段逐个击破，
**每一阶段都用 JMeter 压测给出量化验收指标**。

对应真实业务场景：淘宝双十一、京东 618、小米抢购、茅台预约。

### 要攻克的核心难题

| # | 难题 | 本质 |
|---|---|---|
| 1 | 瞬时高并发流量 | 请求量达平时数十~上百倍，打满服务器/数据库连接池 |
| 2 | 库存超卖 | 10000 人抢 100 件，如何保证不多卖 |
| 3 | 重复下单 | 同一用户多次秒杀成功 |
| 4 | 黄牛刷单 | 脚本 / 机器人 / 多账号，如何保障公平性 |
| 5 | 服务雪崩 | 下游（订单、支付）变慢引发级联故障 |
| 6 | 数据一致性 | Redis 预减库存成功但数据库落库失败 |
| 7 | 系统可扩展性 | 如何水平扩展 |

## 二、四阶段架构演进（本项目的骨架）

| 阶段 | 做法 | 解决的问题 | 目标指标 |
|---|---|---|---|
| **阶段一** | 基础秒杀系统（数据库直连版） | 暴露超卖、重复下单，建立性能基线 | ≈ 50 QPS |
| **阶段二** | 引入 Redis 缓存层 | 读性能优化，缓存穿透/击穿/雪崩 | 读接口 QPS 显著提升 |
| **阶段三** | 消息队列削峰填谷 | 异步下单，瞬时流量平滑降级 | 写链路可承接万级并发 |
| **阶段四** | 微服务拆分 + 服务治理 | 单体 → 微服务，可扩展、可治理 | **30000+ QPS** |

> 关键心法：**先压测出问题，再优化，再压测验证**。没有压测数据的优化等于拍脑袋。

## 七、学习方法论（重要）

1. **先跑通，再压测，再优化**：每章都按"能跑 → 压测 → 定位瓶颈 → 优化 → 复测"闭环。
2. **记录压测数据**：QPS、RT(P95/P99)、错误率、CPU/内存、DB 连接数，写进 [进度追踪表](./进度追踪表.md)。
3. **刻意制造故障**：MQ 宕机、Redis 宕机、DB 慢查询、重复点击、并发抢购，观察系统行为。
4. **每章沉淀一篇笔记**：问题现象 → 原因 → 方案对比 → 最终选择 → 验证数据。
5. **面试导向**：每章末尾的"面试追问"要能口头讲清楚。

## 九、项目复盘总结（00~09 章已完成）

> 这一节是走完全程之后回头看的东西：做过什么、为什么这么做、踩过什么坑、还差什么。

### 9.1 现在具备的能力

| 能力 | 落地形态 |
|---|---|
| 高并发读 | Caffeine（30s）→ 布隆过滤器 → Redis → MySQL 四级链路 |
| 缓存防护 | 空值缓存防穿透、TTL 抖动防雪崩、预热接口手动触发 |
| 异步下单 | RabbitMQ 削峰，消费端扣库存 + 建单，SSE / 轮询取结果 |
| 库存正确性 | Redis + Lua 原子预扣（活动时间 / 一人一单 / 库存 / 售罄标记） |
| 失败兜底 | 预扣回补 Lua + 发送失败补偿表 + 定时任务指数退避重发 |
| 流量防护 | 用户维度 5 次/10s、IP 维度 50 次/10s，注解 + 切面解耦 |
| 认证 | Sa-Token + Redis，验证码校验走 Lua 保证原子 |

### 9.2 技术选型的因果链

| 当时的困难 | 引入的技术 | 真正换来的东西 |
|---|---|---|
| 先查再改，库存扣成负数 | `UPDATE ... WHERE stock > 0` | 判断与修改不可分割 |
| 同一用户并发下多单 | 唯一索引 + 应用层锁 | 前者防错，后者省开销 |
| 详情页 QPS 上不去 | 多级缓存 + 布隆 + 空值 | 把慢的挡在门外 |
| 缓存整点集体失效 | TTL 随机抖动 | 一个 `+random()` 换一次免于雪崩 |
| 写链路被 DB 事务拖死 | RabbitMQ | 从悬崖变缓坡 |
| `DECR` 扣出负数 | Lua 脚本 | 把临界区搬进 Redis |
| 预扣成功 MQ 发失败 | 回补 Lua + 补偿表 | 宁可少卖，不可超卖 |
| 脚本刷接口 | 用户 + IP 双维度限流 | 把恶意流量挡在业务之前 |

**一句话记：缓存让数据库少挨打，MQ 让请求排队，Lua 让临界区不需要锁，限流让系统对剩下的人还能快。**

### 9.3 六个真实踩过的坑（比代码值钱）

1. **Lua 里 `remainStock` 忘了赋值** → Redis 沙箱直接报 `nonexistent global variable`，下单接口 100% 500。教训：Redis 的 Lua 比普通 Lua 严格，`local` 不是可选项。
2. **售罄标记没人清理** → 库存还有 20，用户却看到"已售罄"。教训：标记的生命周期必须有人负责，预热要连标记一起复位。
3. **`@ApiOperationLog` 序列化 `HttpServletRequest`** → `getInputStream() has already been called`，接口必现 500。教训：切面不能无差别序列化入参。
4. **`@Recover` 签名不匹配** → 兜底方法静默失效，失败没人知道。教训：第一个参数必须与 `retryFor` 完全一致，且必须跨 bean 调用。
5. **补偿表里 `setStatus` 当成了落库** → 只改内存对象，数据库没动。教训：看起来像更新 ≠ 真的更新。
6. **IP 维度限流打死压测** → 1000 个请求同 IP，全被 50 次/10s 拦掉。教训：压测前要么调大阈值，要么临时摘掉注解。

### 9.4 当前遗留问题

- 每单约 **9 次 Redis 往返**，而 Lettuce 连接池 `max-active: 20`、Tomcat 默认 200 线程，高并发下排队明显；
- `log4j2` 把 `com.practice.flashsale` 与 `common.mapper` 开到 **DEBUG**，MyBatis 还开着 `log-impl`，压测前必须关；
- 下单前两次 `hasKey` 与 Lua 内校验重复，可删；
- 第 10 章的微服务化（Nacos / Gateway / Sentinel）**代码层面尚未落地**，仍是单体多模块；
- 预热只能手动触发（`POST /admin/goods/cache/preheat`），没有定时任务兜底。

### 9.5 面试一句话速查

- **为什么不用 JWT**：商品可以抢不到，账号不能踢不掉。
- **为什么用 Lua**：Redis 保证一条命令不被打断，Lua 保证一组命令不被打断。
- **为什么先删缓存不更新**：更新可能写了个没人要的值，删除才是幂等的。
- **为什么唯一索引是最后防线**：它是唯一不依赖代码正确性的约束。
- **为什么削峰不直接加机器**：加机器解决"平均能力"，解决不了"瞬时尖峰"。
- **为什么补偿而不是分布式事务**：能靠补偿解决的，别用全局锁锁死。
