## 二、核心问题与解法

### 问题 1：超卖

**朴素写法（有 Bug）**

```java
// ❌ 先查再改，两步之间没有任何保护
Stock stock = stockMapper.selectById(id);
if (stock.getStock() > 0) {
    stockMapper.updateStock(id, stock.getStock() - 1);
}
```

**方案对比**

| 方案 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| SQL 条件判断 | `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0` | 简单、无锁开销、走行锁 | 库存 > 0 时不区分用户，需配合其他手段 |
| 乐观锁 | `UPDATE ... SET stock = stock-1, version = version+1 WHERE id=? AND version=?` | 无长时间锁 | 冲突高时大量失败重试，吞吐低 |
| 悲观锁 | `SELECT ... FOR UPDATE` | 强一致 | 串行化，QPS 极低（基线 50 的主因之一） |

> **结论（专栏路线）**：先用 SQL 条件判断解决超卖，因为它在数据库层面天然利用行锁保证原子性，且代码改动最小。后续阶段会用 Redis Lua 把这一步彻底挪出 DB。

### 问题 2：重复下单

- **兜底**：`t_seckill_order` 上 `(user_id, seckill_goods_id)` 唯一索引，插入冲突即抛异常返回"请勿重复下单"
- **优化**：在唯一索引基础上加**应用层锁**，把重复请求挡在业务逻辑之前，减少无谓的 DB 开销
  - 单机：`synchronized` / `ReentrantLock` / Caffeine 本地锁
  - 多机：Redisson 分布式锁 `lockKey = "seckill:order:" + userId`
- **注意**：锁的粒度要按用户维度，不能按商品维度（否则所有人都串行）

## 七、常见坑

- 事务范围过大（把 HTTP 调用、Redis 操作放进事务）导致连接池被长时间占用
- `synchronized` 加在方法上而不是按用户加锁 → 全站串行
- 唯一索引冲突时未捕获 `DuplicateKeyException`，接口直接 500
- JMeter 未做参数化，100 个线程其实是同一用户 → 测不出真实并发
- 压测机与压测目标在同一台机器上，互相抢资源导致数据失真

## 八、面试追问

### 8.0 当时到底卡在哪

**卡点一：库存被扣成了负数。**

100 个线程抢 10 件商品，跑完一看 `seckill_stock = -87`，订单表里躺着 97 条记录。原因就一句：**先查再改**。查的时候大家都看到"还有 1 件"，改的时候大家各减各的，中间那段空白没人管。

**卡点二：同一个用户抢到了 6 单。**

拿同一个 Token 并发 10 次下单，成功了 6 次。用户自己都没反应过来，购物车里多了 6 件秒杀商品。

**卡点三：一加锁，QPS 从 50 掉到 8。**

为了修重复下单，我把 `synchronized` 直接加在下单方法上。结果所有用户排队进这一个方法——本来毫不相干的两个人，被我硬生生做成了全站串行。

### 8.1 为什么最后引入了这些技术

**SQL 条件扣减**，引入它是为了：

- 不是为了让代码变短，而是为了让"判断"和"扣减"压进同一条语句、同一个瞬间；
- 不是为了绕开事务，而是为了让 InnoDB 的行锁替你守住那道门；
- 不是为了优雅，而是为了正确——**先查再改是两件事，条件更新是一件事**。

**唯一索引**，引入它是为了：

- 不是多一个约束，而是立一块谁都绕不过去的界碑；
- 不是防君子，而是防那些藏在并发缝隙里的重复请求；
- 不是第一道防线，而是最后一道防线——**前面的锁都可能失效，数据库的约束不会**。

**应用层锁**，引入它是为了：

- 不是锁住商品，而是按用户分开排队；
- 不是拦住正常用户，而是拦住同一个人的第二次、第三次点击；
- 不是替代数据库，而是把无效流量挡在事务之外——**锁要锁到人，不能锁到货**。

### 8.2 面试追问（附参考答案）

**Q1：乐观锁和悲观锁在秒杀场景下各适合什么情况？**

A：
- **悲观锁**（`SELECT ... FOR UPDATE`）适合**冲突激烈、必须一次成功**的场景，比如账户余额扣减。代价是串行化，秒杀这种"抢不到就算了"的业务用它，等于把万人抢购做成单窗口排队。
- **乐观锁**（`version` 字段）适合**冲突较少**的场景。冲突一高，大量请求失败重试，重试又是新的数据库压力，吞吐反而更低。
- **秒杀的实际选择**：用 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0` 这种条件更新。它既不是悲观锁把行锁住等，也不是乐观锁先读后比，而是**把判断交给数据库在执行的那一瞬间完成**。
- 再往后走一步，就是把这一步彻底挪出 MySQL，交给 Redis + Lua（第 07 章）。

**Q2：为什么唯一索引是防重复下单的最后一道防线？**

A：因为它是**唯一一个不依赖应用代码正确性**的约束。
- 应用层锁可能因为服务重启、锁过期、多实例竞争而失效；
- 幂等判断可能因为"先查后插"的并发间隙而漏掉；
- 但数据库的唯一索引在**插入的那一刻**做检查，冲突就报错，没有中间态。

所以正确姿势是：**前面用锁和 Redis 标记做优化（少打数据库），最后一层用唯一索引兜底（保证不出错）**。项目里 `uk_user_activity(user_id, seckill_goods_id)` 就是这道兜底。要注意捕获 `DuplicateKeyException` 并当成"已下单"处理，而不是直接 500。

**Q3：`UPDATE ... WHERE stock > 0` 为什么能防超卖？底层靠什么保证？**

A：因为"判断库存是否大于 0"和"把库存减 1"发生在**同一条 SQL、同一个执行单元**里，中间没有给任何人插队的机会。

底层靠的是 **InnoDB 的行级排他锁**：
1. 事务执行 UPDATE 时先给目标行加 X 锁；
2. 其他事务的 UPDATE 在同一行上排队等待；
3. 等它拿到锁时，库存已经被前一个事务改过了，`stock > 0` 这个条件重新判断，不满足就影响 0 行。

所以并发 100 个请求打过来，MySQL 会把它们排成一队，逐个判断、逐个扣减，扣到 0 之后剩下的全部返回 0 行。**判断和修改不可分割，超卖就无从发生。**

**Q4：加了应用层锁之后 QPS 反而下降，可能是什么原因？**

A：四个常见原因，按踩坑概率排序：
1. **锁粒度错了**：锁按商品加（`lock:goods:{goodsId}`），所有抢同一件商品的人排成一队，等于全站串行。正确是按用户加（`lock:user:{userId}`）。
2. **锁的范围包住了慢操作**：把 Redis 调用、MQ 发送、甚至 HTTP 请求都圈进锁里，锁的持有时间被拉到几十毫秒。
3. **锁本身的开销**：Redisson 分布式锁一次加锁解锁就是两三次 Redis 往返，比业务逻辑本身还贵。
4. **锁等待变成排队**：高并发下大部分时间花在等锁，而不是干活。

结论：**锁是用来挡重复的，不是用来挡并发的。** 能不用锁就不用锁，能用 Redis 标记（`SETNX`）就不用分布式锁。

**Q5：你的基线 QPS 是多少？瓶颈在 CPU、连接池还是数据库？**

A：基线在 **50 QPS 量级**，P99 已经上百毫秒。瓶颈定位方法：
- 看 **HikariCP 活跃连接数**是否长期贴着 `maximum-pool-size`，是 → 连接不够或事务太长；
- 看 **MySQL 的 `SHOW PROCESSLIST`** 里有没有大量 `SLEEP`/`Locked`，有 → 锁竞争；
- 看 **CPU 使用率**，如果 CPU 不高但 QPS 上不去，说明线程都在等 IO（数据库/网络），不是算不过来；
- 最后看 **慢查询日志**，确认是不是缺索引导致的全表扫描。

我这里的结论是：**瓶颈在数据库连接和行锁，不在 CPU**——这也正是后面要引入缓存和 MQ 的直接理由。没有这个数字，后面的优化就只是"感觉快了"。
