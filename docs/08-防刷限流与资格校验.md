## 二、限流器实现（Redis Lua 固定窗口）

```lua
-- KEYS[1] = rate:limit:{接口}:{用户或IP}
-- ARGV[1] = 窗口内最大请求数
-- ARGV[2] = 窗口秒数
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
    return 0    -- 被限流
end
return 1        -- 放行
```

**为什么用 Lua**：`INCR` 与 `EXPIRE` 必须原子完成，否则第一个请求设置 TTL 失败会导致 key 永不过期（永久封禁）。

### 限流算法对比

| 算法 | 特点 | 问题 |
|---|---|---|
| 固定窗口 | 实现简单、Redis Lua 即可 | 窗口边界双倍突发 |
| 滑动窗口 | 更平滑 | 需 ZSet 存时间戳，内存开销大 |
| 漏桶 | 恒定速率输出 | 无法应对突发 |
| 令牌桶 | 允许一定突发 | 实现稍复杂（Guava RateLimiter/Redisson RRateLimiter） |

### 注解 + AOP

```java
@RateLimiter(key = "#userId", limit = 5, window = 1, message = "请求过于频繁")
@PostMapping("/seckill/order")
public Result<?> seckillOrder(Long userId, Long goodsId) { ... }
```

> AOP 切面解析 SpEL 得到限流维度（用户/IP/接口），把限流与业务彻底解耦。

## 三、秒杀令牌（Token）机制

**目的**：把"要不要让他进入下单流程"与"下单"分离，用令牌作为准入门槛。

```
步骤 1  用户点击"立即抢购"
        ──► 请求令牌接口 /seckill/token?goodsId=x
        ──► 服务端校验：登录、活动时间、是否已购、限流
        ──► 通过则生成 token 存 Redis：seckill:token:{userId}:{goodsId} = token, TTL 30s
        返回给前端

步骤 2  用户携带 token 请求下单 /seckill/order?goodsId=x&token=xxx
        ──► 服务端 Lua 脚本：GET token → 比对 → DEL（一次性）
        ──► 校验通过 → 执行库存预扣 → 发 MQ
```

### 关键设计

| 设计点 | 说明 |
|---|---|
| 一次性 | 用 Lua 的 `GET`+`DEL` 或 Redis 6.2 的 `GETDEL`，防止 token 重复提交 |
| 令牌大闸 | 发放令牌数量 = 库存数量 × 系数（如 1.2），多余流量在令牌阶段就被拒绝 |
| TTL 短 | 30~60 秒，防止令牌长期囤积 |
| 绑定维度 | `userId + goodsId`，防止令牌串用 |

### 并发 Bug 修复（8.7 重点）

| Bug | 原因 | 修复 |
|---|---|---|
| 重复扣大闸 | "判断余量 → 扣减"非原子 | 用 Lua 把判断与扣减合并为原子操作 |
| token 被覆盖 | 多次请求令牌接口，后发 token 覆盖前一个，导致前一个失效 | 用 `SETNX`，已存在则直接返回旧 token |

## 四、线程池队列泄洪（本地拥塞窗口）

思路：下单接口前面加一个**有界的工作队列 + 有界线程池**，
当队列已满时不等待、**立即返回"活动火爆，请稍后重试"**，
把系统从"雪崩"变成"可控的拒绝"。

```java
private final ThreadPoolExecutor seckillExecutor = new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),                 // 有界！容量即"窗口"
    namedFactory,
    new ThreadPoolExecutor.AbortPolicy()           // 队满直接拒绝，快速失败
);
```

> 核心思想：**宁可拒绝一部分请求，也不让整个系统挂掉**（限流 > 熔断 > 雪崩）。

## 六、验收标准

| 指标 | 要求 |
|---|---|
| 限流生效 | 单用户 1 秒内第 6 次请求被拒，且 key 会正常过期 |
| 令牌一次性 | 同一 token 提交 2 次，第 2 次失败 |
| 令牌大闸 | 令牌发放量 ≤ 库存 × 系数 |
| 泄洪 | 高并发下接口错误码为"排队/稍后重试"而非超时/502 |
| 预热幂等 | 3 个实例同时启动，预热逻辑只执行一次 |

## 七、常见坑

- `INCR` 与 `EXPIRE` 分开执行 → 出现永久限流的 key（**必须用 Lua**）
- 固定窗口边界问题：第 1 秒末 + 第 2 秒初各打满 → 瞬时双倍流量（可用滑动窗口缓解）
- 令牌只生成不删除 → 可以重复提交
- 令牌 TTL 太长 → 黄牛囤积令牌
- 线程池用无界队列 → 请求无限堆积，最终内存溢出（必须有界 + 明确拒绝策略）
- 限流 key 的维度选错（比如只按 IP）→ 同一 WiFi 下正常用户被误伤
- 分布式锁未设置过期时间 → 死锁；未校验持锁线程 → 误删他人锁（Redisson 已解决，自己实现要注意）

## 八、面试追问

### 当时卡在哪

**卡点一：限流代码塞在 Service 里，参数传不进去。**

一开始把限流写在 `OrderServiceImpl` 里，方法签名是 `checkSeckillRateLimit(activityId, goodsId, userId, clientIp)`。写着写着发现 `clientIp` 没人能给——Controller 为了拿 IP 加了个 `HttpServletRequest` 参数，结果又踩了另一个坑：日志切面把 request 当普通 Bean 序列化，触发了 `getInputStream() has already been called`，下单接口 100% 报 500。

最后重构：限流用注解 `@SeckillRateLimit` + 切面，**切面自己用 `RequestContextHolder` 取 request**，Controller 的方法签名保持干净。那次重构后，Service 里那个 `checkSeckillRateLimit` 就成了没人调用的死代码，字段和常量全成了孤儿。

**卡点二：压测数据全被限流"优化"掉了。**

配好 IP 维度 50 次/10 秒后去压测，1000 个并发全从 localhost 发出，**同一个 IP**，结果 95% 的请求直接被判"请求过于频繁"。看报告还以为系统扛不住，其实是自己把闸门关小了。

**卡点三：固定窗口在边界上会"放过双倍"。**

第 1 秒末尾打满 5 次，第 2 秒开头再打满 5 次——两个窗口各算各的，实际 1 秒内过了 10 次。

### 为什么最后是"注解 + 切面"

- 不是为了少写几行代码，而是为了让**限流和业务彻底分开**：业务只管下单，限流只管拦人；
- 不是为了炫技 AOP，而是为了让**阈值可以声明在方法上**：`@SeckillRateLimit(userMaxCount = 5, ipMaxCount = 50)` 一眼就能看懂；
- 不是为了抽象而抽象，而是为了**换维度不用改业务代码**：今天限 IP，明天加设备指纹，只动切面和注解。

**限流不是拦用户，是拦那些不该进来的流量；不是让系统变慢，是让系统对剩下的人还能快。**

### 面试追问（附参考答案）

**Q1：固定窗口限流有什么缺陷？怎么改进？**

A：缺陷是**窗口边界上的流量翻倍**。窗口是 [0s, 10s] 和 [10s, 20s]，如果在 9.9s 打满 5 次、10.1s 再打满 5 次，这 0.2 秒内实际放过了 10 次——瞬时压力是阈值的两倍。

三种改进：
- **滑动窗口**：用 Redis ZSet 存每次请求的时间戳，统计"最近 10 秒内的请求数"。精确，但内存和复杂度都上去了。
- **令牌桶**：按固定速率往桶里放令牌，请求消耗令牌。允许一定程度的突发，工程上最常用。
- **漏桶**：请求先进队列，按固定速率流出。绝对平滑，但会引入排队延迟。

秒杀场景其实**不太在乎这点边界误差**——真正要拦的是"脚本每秒几千次"，不是"边界上多过 5 次"。所以项目用固定窗口 + Lua 就够了，简单、够用、好维护。

**Q2：秒杀令牌和普通限流有什么区别？为什么需要大闸？**

A：**限流是"按频率拦"，令牌是"按资格放"。**

- 普通限流：同一用户 10 秒内最多 5 次，超了就拒——它控制的是**频率**；
- 秒杀令牌：抢购开始前先调接口领一张令牌（有 TTL、一次性），下单时必须带着令牌——它控制的是**资格**。

为什么需要"大闸"（令牌总量控制）：秒杀开始瞬间可能有 10 万人同时点，但库存只有 100 件。如果全放进来做 Redis 扣减，10 万次请求就是 10 万次 Redis 往返 + 10 万次后续的"售罄"响应。令牌大闸的做法是**只发 200 张令牌**（比如库存的 2 倍），剩下的人在第一道闸就被挡住，**用最小的成本拒绝最多的无效请求**。

一句话：**限流管"你来得太快"，令牌管"你有没有票"。**

**Q3：为什么限流要用 Lua 保证原子性？分开写会怎样？**

A：因为限流的核心是"**计数 + 判断**"，这两步分开写就有并发缝隙。

分开写的典型实现是 `INCR` 然后 `GET` 判断，或者 `GET` 判断然后 `INCR`：
- `GET` 判断时大家都看到 4（还没到 5），于是 100 个请求同时判断通过，然后一起 `INCR`，计数直接冲到 104；
- 即使只用 `INCR` 的返回值判断，也要额外处理"第一次设置 TTL"的问题——`INCR` 和 `EXPIRE` 之间如果进程崩了，就会留下一个**永不过期的计数器**，这个用户的额度被永久锁死。

Lua 把 `INCR`、首次 `EXPIRE`、阈值比较包成一次原子执行，既没有并发缝隙，也不会漏设过期时间。项目里的 `seckill_rate_limit.lua` 就是这三步。

**Q4：令牌如何保证只能用一次？**

A：靠**原子地"取走并删除"**。

错误写法是 `GET` 判断存在 → `DEL` 删除，两步之间有窗口，两个请求可以同时判断"存在"，然后各删各的，令牌被用了两次（和验证码重放是同一个坑）。

正确写法是 Lua 或 `GETDEL`：
- 读取令牌的**同时**删除，删除成功才算拿到；
- 或者把令牌的 value 设为一次性随机串，删除时校验 value 匹配；
- 再配合 TTL，防止黄牛提前领一堆令牌囤着。

**关键点：令牌必须是"一次性消耗品"，不能是"永久通行证"。**

**Q5：线程池队列满了，应该丢弃还是等待？为什么？**

A：都不能"无脑"选，要看业务语义。

- **不能无界等待**：队列无界只是把 OOM 推迟，请求堆在内存里，最终内存爆掉，连累整个进程。
- **不能全部丢弃**：秒杀场景里用户点了按钮，你静默丢弃，用户会一直等，体验比明确拒绝还差。
- **正确做法是"有界队列 + 明确的拒绝策略"**：
  - `AbortPolicy`：直接抛异常，接口立刻返回"系统繁忙"，用户能重试；
  - `CallerRunsPolicy`：让调用线程自己执行，天然形成"反压"，把压力传导回请求方；
  - 自定义：记录日志 + 返回友好错误码，绝不能假装成功。

秒杀场景推荐**快速失败 + 明确提示**：**宁可告诉用户"没抢到"，也不能让用户"一直等一个永远不会来的结果"。**

**Q6：Redisson 分布式锁的看门狗机制是什么？**

A：解决的问题是"**锁的过期时间比业务执行时间短**"。

- 加锁时如果不指定 `leaseTime`，Redisson 默认给 30 秒过期，同时启动一个**后台定时任务（看门狗）**；
- 看门狗每隔 `30/3 = 10` 秒检查一次：如果当前线程还持有锁，就把过期时间**重置回 30 秒**；
- 业务执行完 `unlock()` 后，看门狗停止续期，锁被释放。

它的价值：**你不需要猜"业务要跑多久"**。猜短了锁提前释放，别的线程进来导致并发问题；猜长了，一旦进程崩溃，锁要等很久才释放。

注意两点：
1. 看门狗只在**不指定 `leaseTime`** 时生效；显式传了 `leaseTime`，Redisson 不会续期。
2. 看门狗依赖 JVM 存活。**进程被 kill -9 之后，锁最多 30 秒自动释放**——这反而是好事，避免了死锁。

**Q7：如何识别黄牛？**

A：单看一个维度都能被绕过，要**多维度叠加打分**：

| 维度 | 信号 |
|---|---|
| **账号** | 新注册、无历史订单、资料空白、批量规律的用户名 |
| **设备** | 同一设备指纹登录多个账号、模拟器特征、越狱/Root |
| **IP** | 同 IP 短时间大量请求、IP 归属地集中、代理池特征 |
| **行为** | 请求间隔精确到毫秒（人类做不到）、页面停留时间几乎为 0、只点"立即购买"不做任何浏览 |
| **收货地址** | 大量账号填同一地址/同一手机号 |

工程上的做法是**分层处置**，不是一刀切：
- 低风险：正常放行；
- 中风险：加验证码 / 滑块，提高成本；
- 高风险：限流 / 排队 / 直接拒绝，并加入黑名单。

一句话：**黄牛不怕你拦得狠，怕你拦得"不确定"——让他算不清成本，比一次封号更有效。**
