## 二、库表设计要点

### 核心表

| 表名 | 说明 | 关键约束 |
|---|---|---|
| `t_user` | 用户 | `username` / `phone` 唯一索引 |
| `t_goods` | 商品（SPU + 价格、库存展示） | — |
| `t_seckill_activity` | 秒杀活动 | 关联商品，`start_time` / `end_time` |
| `t_seckill_goods` | 秒杀商品（活动下的商品快照） | 库存、秒杀价、每人限购数 |
| `t_seckill_order` | 秒杀订单 | **`uk_user_activity(user_id, seckill_goods_id)` 唯一索引** |
| `t_pay_order` | 支付单 | 订单号唯一 |

### 设计原则

1. **防重复下单靠唯一索引兜底**：`t_seckill_order` 上建 `(user_id, seckill_goods_id)` 唯一索引，这是最后一道防线，应用层锁只是性能优化。
2. **库存字段用 `int` 且允许 `CHECK (stock >= 0)`（MySQL 8 支持）**，避免负库存。
3. **金额用 `decimal(10,2)`**，禁用 `float/double`。
4. **时间字段统一 `datetime`**，不用时间戳，便于排查。
5. **高频查询字段要建索引**：活动起止时间、商品 id、订单状态。
6. **预留乐观锁版本号 `version`**（若采用乐观锁方案）。

### 示例（下单核心 SQL 的"防超卖"写法）

```sql
UPDATE t_seckill_goods
SET stock = stock - 1
WHERE id = #{seckillGoodsId}
  AND stock > 0;   -- 关键：把判断和扣减放到同一条 SQL，利用行锁保证原子性
```

> 若 `affectedRows = 0`，说明库存已空，直接返回"已售罄"。

## 三、多模块工程结构建议

```
FlashSaleSystem
├── flash-sale-common        通用：统一响应、异常、常量、工具类
├── flash-sale-dao           实体、Mapper 接口、XML
├── flash-sale-service       业务逻辑
├── flash-sale-web           启动类、Controller、配置、拦截器
└── docs                     学习文档
```

依赖方向：`web → service → dao → common`，**严格单向，禁止反向依赖**。

### 分层规范

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 参数校验、协议转换、调用 Service | 写业务逻辑、直接调 Mapper |
| Service | 业务编排、事务边界 | 处理 HTTP 细节 |
| Mapper | 单表/简单多表 CRUD | 写复杂业务判断 |

## 六、常见坑

- 唯一索引只加在应用层没落库 → 并发下必然重复下单
- HikariCP `maximum-pool-size` 设得过大（如 200），反而因线程上下文切换导致 QPS 下降；参考公式 `connections = ((core_count * 2) + effective_spindle_count)`
- MyBatis 的 `#{}` 与 `${}` 混用导致 SQL 注入
- Log4j2 与 Spring Boot 默认 Logback 冲突，需要排除 `spring-boot-starter-logging`
- Disruptor 缓冲区大小必须是 2 的幂

## 七、面试追问

### 当时卡在哪

**卡点一：表结构返工了两次。**

第一版把秒杀价、秒杀库存直接加在 `t_goods` 上，结果一个商品要参加两场活动就没地方放了——活动和商品是"一对多"，被我做成了"一对一"。第二次改表时，前面写的代码全得跟着改。

**卡点二：连接池大小是拍脑袋写的。**

看到别人配置 `maximum-pool-size: 200` 就照抄，压测发现 QPS 反而比 50 还低。后来才明白：**连接数不是越多越能打，而是越多越会抢。**

**卡点三：多模块拆得心里没底。**

一开始想把 `user` / `goods` / `order` 拆成三个独立工程，后来发现它们都要用 `Result`、`BizException`、`RedisKeyConstants`——每拆一次就要复制一份，最后变成"三份一样的代码，改一处忘两处"。

### 为什么最后这么设计

- **表设计不是为了"少建表"，而是为了让"一对多"有地方落脚**：活动是一张表，活动下的商品是另一张表，商品本身又是一张表，三层各管一段；
- **连接池不是越大越好，而是越"匹配"越好**：数据库是有限的，连接是有限的，线程也是有限的，**三个有限的资源凑一起，多给谁都不对**；
- **模块拆分不是为了"看起来专业"，而是为了让依赖单向、公共下沉**：能沉到 `seckill-common` 的绝不复制，能单向依赖的绝不成环。

### 面试追问（附参考答案）

**Q1：唯一索引能防重复下单吗？高并发下会怎样？**

A：**能，而且它是最可靠的一层**，但要理解它的代价和行为。

- 高并发下，两个请求同时插入同一组 `(user_id, seckill_goods_id)`，数据库会在索引层面串行化，**一个成功、一个抛 `DuplicateKeyException`**，不会出现"两个都成功"。
- 代价是：冲突的请求要走到数据库才被拒，**前面所有业务逻辑（查元数据、扣 Redis 库存）都白做了**。所以它适合作"最后一道防线"，不适合作"唯一防线"。
- 工程上要配两道：**Redis 的购买标记做前置拦截（快），唯一索引做兜底（稳）**。并且必须捕获 `DuplicateKeyException` 转成友好提示，否则用户看到的是 500。

**Q2：HikariCP 连接池大小怎么定？为什么不是越大越好？**

A：常用起点公式是 `connections = CPU 核数 × 2 + 磁盘数`，但真正该做的是**压测找拐点**。

为什么不是越大越好：
1. **数据库侧有硬上限**。MySQL 的 `max_connections` 是有限的，应用侧开 200 个连接，只会让数据库在 200 个线程之间切换上下文，每个查询都变慢。
2. **连接本身有成本**。每个连接占内存、占文件描述符，空闲连接还要被心跳检测。
3. **连接多 ≠ 并发高**。真正的并发度取决于 CPU 核数，连接池只是"排队缓冲区"。缓冲区太大，问题会被掩盖而不是被解决。

项目里配的是 `maximum-pool-size: 50`、`minimum-idle: 10`，属于小规模够用；如果是"连接数长期贴顶"，正确做法是先看**事务是不是太长**，而不是直接调大。

**Q3：秒杀订单表为什么要独立于普通订单表？**

A：三个理由：

1. **写入特征完全不同**。普通订单是低频、可随时写入；秒杀订单是瞬时、集中在几秒内爆发。混在一起会让普通订单在秒杀期间被拖慢。
2. **字段和索引诉求不同**。秒杀订单需要 `(user_id, seckill_goods_id)` 唯一索引、需要按活动和商品维度统计；普通订单更关注支付状态、物流、售后。
3. **数据生命周期不同**。秒杀订单往往要在活动结束后归档、清理，独立成表便于按表操作，不用在大表上做 `DELETE`。

一句话：**秒杀表为"冲击"设计，普通表为"长跑"设计，混在一起两边都难受。**

**Q4：多模块拆分的依据是什么？拆太细有什么问题？**

A：拆分依据是**变更频率和依赖方向**，不是"看起来像几个业务"。

- **按业务边界拆**：user / goods / order 各自有独立的实体、Mapper、Service；
- **按依赖方向拆**：`app` 依赖三个业务模块，业务模块依赖 `common`，**业务模块之间绝不互相依赖**；
- **公共能力下沉**：`Result`、异常、Redis key、工具类全放 `common`，避免复制。

拆太细的问题：
1. **公共代码被迫复制**，或者催生一个"什么都有"的 common，反而更乱；
2. **模块间调用变多**，如果迟早要拆成独立服务，模块边界没设计好就是给未来挖坑；
3. **构建变慢**，`mvn` 要串行编译一串模块。

判断标准：**如果一个模块只有两三个类、且只被一个模块使用，就不该独立成模块。**
