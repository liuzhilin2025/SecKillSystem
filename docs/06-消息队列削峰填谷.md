## 二、削峰填谷到底削的是什么

```
同步模式：
10000 请求 ──┐
             ├──► 业务线程 ──► DB（被打爆，大量超时）
             ┘    （线程池瞬间耗尽）

异步模式：
10000 请求 ──► Redis 校验 ──► MQ（消息堆积，但接口立刻返回"排队中"）
                                    │
                       消费者按自己的节奏消费（平滑速率）──► DB
```

**它削的不是"流量"，而是"流量的形状"。**

请求总量一个没少，但到达数据库的方式从"一次性砸过来"变成了"匀速流进来"。数据库最怕的从来不是总量大，而是**在极短时间里被同时要求处理大量事务**——那意味着锁竞争、连接耗尽、超时连锁。

三层收益，按重要性排序：

1. **请求线程被解放**：HTTP 线程只负责"校验 + 入队 + 回执"，不再等待数据库事务。接口 RT 从"受数据库心情影响"变成"受 Redis 心情影响"。
2. **数据库被匀速对待**：消费者的速率是可控的（`prefetch` + `concurrency`），数据库永远只面对它扛得住的并发。
3. **系统按平均能力设计**：不用为了 3 秒的峰值去买能扛 1 万并发的机器，成本差一个数量级。

**代价必须一起说清楚**：一致性从"强"变成"最终"，链路从"一段"变成"一长串"，排错难度上一个台阶。所以异步化的同时，必须配套**结果通知**和**失败补偿**，否则就是把问题从接口转移给了用户。

## 三、逐小节：怎么做 + 为什么

### 6.1 Docker 安装 RabbitMQ

**做什么**：起一个带管理台的 RabbitMQ，并规划好端口和 vhost。

**怎么做**：

```bash
docker run -d --name rabbitmq \
  -p 5673:5672 -p 15673:15672 \
  -e RABBITMQ_DEFAULT_USER=seckill \
  -e RABBITMQ_DEFAULT_PASS=Seckill2024ABC \
  -e RABBITMQ_DEFAULT_VHOST=/seckill \
  rabbitmq:3-management
```

> 本项目实际用的就是 **5673** 端口和 **`/seckill`** 虚拟主机（见 `application-dev.yml`），不是默认的 5672。

**为什么**：

- **为什么用 Docker**：这个项目要同时跑 MySQL、Redis、RabbitMQ 三个中间件。本机各装一份，版本、端口、配置文件互相污染，卸载还卸不干净。容器化之后，"删了重来"只需要一条命令。
- **为什么必须带 `-management`**：削峰的效果**只能靠队列堆积曲线来证明**。没有管理台，你看不到"消息进来多少、消费掉多少、还剩多少"，就只能靠猜。
- **为什么要单独设 vhost**：vhost 是 RabbitMQ 的逻辑隔离单元，不同项目共用一台 Broker 时，队列名不会撞。用默认 `/` 迟早会和别的项目打架。

**不这么做会怎样**：用默认 `guest/guest`，只能本机访问；不设 vhost，队列名全局唯一，换项目就得改名。

### 6.2 Spring Boot 整合：交换机、队列、绑定

**做什么**：把"消息往哪发、发到哪个队列、失败去哪"用代码声明出来，并统一消息格式为 JSON。

**怎么做**（`RabbitMQConfig` 的实际结构）：

```java
// 1. 业务交换机（Direct，持久化）
@Bean
public DirectExchange seckillOrderExchange() {
    return new DirectExchange(SECKILL_EXCHANGE, true, false);
}

// 2. 业务队列（持久化 + 挂死信）
@Bean
public Queue seckillOrderQueue() {
    return QueueBuilder.durable(SECKILL_QUEUE)
            .withArgument("x-dead-letter-exchange", SECKILL_DLX_EXCHANGE)
            .withArgument("x-dead-letter-routing-key", SECKILL_DLX_ROUTING_KEY)
            .build();
}

// 3. 绑定
@Bean
public Binding seckillOrderBinding(Queue seckillOrderQueue, DirectExchange seckillOrderExchange) {
    return BindingBuilder.bind(seckillOrderQueue)
            .to(seckillOrderExchange)
            .with(SECKILL_ROUTING_KEY);
}

// 4. 统一 JSON 序列化
@Bean
public MessageConverter messageConverter() {
    return new Jackson2JsonMessageConverter();
}
```

命名规范：

| 类型 | 名称 |
|---|---|
| 业务交换机 | `seckill.order.exchange` |
| 业务队列 | `seckill.order.queue` |
| 路由键 | `seckill.order.create` |
| 死信交换机 | `seckill.order.dlx.exchange` |
| 死信队列 | `seckill.order.dlx.queue` |
| 死信路由键 | `seckill.order.dlx` |

**为什么**：

- **为什么用 Direct 而不是 Fanout / Topic**：秒杀下单只有一条确定的链路，路由键是固定的 `seckill.order.create`。Direct 是精确匹配，最简单也最快。Topic 的通配符能力这里用不上；Fanout 会把消息广播给所有绑定的队列，一旦有人绑错队列，消息就会重复消费。
- **为什么 `durable = true`**：Broker 重启后，交换机和队列本身要还在。不持久化的话，重启意味着"队列不存在了"，里面的消息直接消失。
- **为什么队列声明时就带死信参数**：死信不是在代码里"try-catch 转发"，而是**队列本身的属性**。消息被 nack 且 `requeue=false` 时，Broker 自动把它投到死信交换机——**这个动作不依赖消费者是否还活着**。
- **为什么用 JSON 而不是 JDK 序列化**：JDK 序列化会把完整类名写进字节流，改个包名就反序列化失败，而且管理台看到的是一堆乱码。JSON 可读，排查时直接看消息内容就行。

**不这么做会怎样**：`durable=false` + Broker 重启 = 堆积的消息全丢；用 JDK 序列化 = 管理台看不到内容，出问题只能靠猜；不带死信参数 = 失败消息只能丢弃或无限重投（见 6.8）。

### 6.3 异步下单架构：四段式

**做什么**：把"一次下单"拆成四个职责清晰、时间尺度完全不同的阶段。

```
① 前置校验   令牌 → 活动时间 → 一人一单预检        （Redis，1~3ms）
② 入队       发 MQ，立即返回 orderNo + PROCESSING   （1~2ms）
③ 异步落库   扣库存 + 建订单（编程式事务）          （10~100ms，受并发影响）
④ 结果通知   写状态 + SSE 推送 / 前端轮询           （取决于用户何时来取）
```

**为什么这么拆**：

- ①② 是**内存操作**，快且稳定；
- ③ 是**数据库操作**，慢且不稳定，并发一高就抖动；
- ④ 是**用户感知**，时间尺度最长。

**把最慢、最不稳定的 ③ 从请求线程里剥离，接口的 RT 就只取决于 ①②。** 这就是削峰的全部秘密——不是让 ③ 变快，而是让用户不等 ③。

**不这么做会怎样**：接口 RT 被数据库事务长度绑死。你压测时看到的 167ms 平均 RT，主要就是线程在等数据库连接和行锁。

### 6.4 生产端：状态预写 → 入队 → 立即返回

**做什么**：改造 `OrderServiceImpl` 的下单入口，让它只做"校验 + 入队 + 回执"。

**怎么做**（`processSeckill` 的核心三步）：

```java
// 1. 先记录异步处理状态，供前端后续查询
saveOrderStatus(userId, orderNo, OrderStatusEnum.PROCESSING.getStatus());

// 2. 发送 MQ（内部携带 CorrelationData = orderNo，供确认回调定位消息）
boolean isSendSuccess = seckillOrderMessageSender.send(seckillOrderMqDTO);

if (!isSendSuccess) {
    log.warn("==> 秒杀下单消息发送结果未知，订单保持处理中等待后续确认, orderNo：{}", orderNo);
}

// 3. 立即响应"处理中"，不再干等那 ~100ms 的写库操作
return DoSeckillRspVO.builder()
        .orderNo(orderNo)
        .status(OrderStatusEnum.PROCESSING.getStatus())
        .build();
```

消息体 `SeckillOrderMqDTO` 携带：`userId`、`activityId`、`goodsId`、`seckillGoodsId`、`goodsName`、`goodsImg`、`seckillPrice`、`orderNo`、`requestTime`。

**为什么**：

- **为什么先写 PROCESSING 状态、再发消息**：如果顺序反过来，消费端可能比生产端更快地把状态改成"待支付"，随后被生产端的"处理中"覆盖回去——**用户明明抢到了，页面却一直显示处理中**。先写状态，是为了让状态机只能往前推，不能往回退。
- **为什么消息体要带 `goodsName` / `goodsImg`**：消费端建订单时不用再查商品表，**一条消息自包含**。消费端依赖越少，消费越快、越不容易失败。
- **为什么用 `orderNo` 作为 `CorrelationData`**：Confirm 回调只能拿到 correlationData，拿不到业务参数，靠它才能定位是哪一单失败了。
- **为什么不在这里等 Confirm**：等就变成同步了，削峰的意义瞬间消失。发送失败由异步补偿兜底（第 09 章的补偿表）。

**不这么做会怎样**：状态被覆盖 → 用户看到"处理中"卡死；消息体缺字段 → 消费端每条消息都要回查数据库，消费速度直接腰斩。

### 6.5 压测：同步 vs 异步

**做什么**：同一份 JMeter 脚本，跑两遍，对比同步版和异步版。

**怎么做**：除了常规指标，**必须同时记录这四个**：

| 指标 | 意义 |
|---|---|
| 平均 RT / P95 / P99 | 接口是否真的变快了 |
| QPS / 错误率 | 系统能接住多少 |
| **DB 活跃连接数** | 数据库是否真的被解放 |
| **队列堆积曲线（生产速率 vs 消费速率）** | 削峰是否真的"削得住" |

**为什么**：

只看 RT 是自欺欺人。异步化之后 RT 一定降——但**如果队列一直堆积、消费永远追不上生产，那只是把"接口慢"变成了"结果永远出不来"**。

判断标准是：**峰值过后，队列能在多长时间内消化干净。** 如果 10 秒的洪峰要 10 分钟才能消费完，用户早就关页面了。

**不这么做会怎样**：看到 RT 从 167ms 降到 5ms 就宣布成功，实际上用户等了 10 分钟才拿到订单——**指标好看，体验崩了**。

### 6.6 并发消费：别再让一个线程扛所有消息

**做什么**：把监听器的并发度提上去。

**怎么做**：

```java
@RabbitListener(queues = RabbitMQConfig.SECKILL_QUEUE, concurrency = "5-10")
public void consume(SeckillOrderMqDTO dto, Channel channel, Message message) throws IOException {
```

`"5-10"` 表示最少 5 个消费者、最多 10 个，Spring AMQP 按负载自动伸缩。

**为什么**：

- `@RabbitListener` **默认单消费者、单线程**，一次处理一条。生产端每秒几千条、消费端每秒几十条，队列只会往上涨。
- **为什么上限是 10 而不是 100**：消费线程最终都要打数据库。线程数超过数据库连接池（`maximum-pool-size: 50`）意义不大，多出来的线程只会在连接池上排队，白白增加上下文切换。

**不这么做会怎样**：队列堆积 → 用户等结果等到 SSE 超时 → 前端显示"查询失败"，而订单其实已经建好了。

### 6.7 消费速率控制：`prefetch` 与 `concurrency` 的分工

**做什么**：给每个消费者设定"手上最多拿几条未确认的消息"。

**怎么做**：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual
        prefetch: 5          # 每个消费者最多 5 条未 ACK
```

**为什么**：

- `concurrency` 决定**开几个窗口**，`prefetch` 决定**每个窗口一次能拿几张单**。
- `prefetch = 0`（无限制）→ 第一个消费者会把队列里的消息全卷走，其他消费者闲着，**负载严重不均**；
- `prefetch = 1` → 每处理一条都要往返一次 Broker，吞吐上不去；
- `prefetch = 5` → 手上有一小批，处理完再取，既并行又不囤积。

**不这么做会怎样**：`prefetch` 无限制 + 某条消息处理特别慢 → 这个消费者手上的后续消息全部堵着，而其他消费者无活可干，整体消费速度反而下降。

### 6.8 消费者可靠性：手动 ACK + 死信队列

**做什么**：业务成功才确认，失败交给死信队列。

**怎么做**：

```java
@RabbitListener(queues = RabbitMQConfig.SECKILL_QUEUE, concurrency = "5-10")
public void consume(SeckillOrderMqDTO dto, Channel channel, Message message) throws IOException {
    long deliveryTag = message.getMessageProperties().getDeliveryTag();

    try {
        orderService.createSeckillOrder(dto);
    } catch (Exception e) {
        log.error("## 秒杀订单消息处理出现系统异常，进入死信队列, orderNo：{}", dto.getOrderNo(), e);
        // requeue = false：不重新入主队列，交给死信队列兜底
        channel.basicNack(deliveryTag, false, false);
        return;
    }

    channel.basicAck(deliveryTag, false);
}
```

**为什么**：

- **为什么必须手动 ACK**：自动 ACK 在"消息投递给消费者"那一刻就确认了，此时业务一行还没执行。消费者这时崩溃，消息已经没了——**数据库里没订单，队列里也没消息，彻底丢**。
- **为什么 `requeue = false`**：`requeue = true` 会让失败消息立刻回到队首，被同一个消费者再次拿到、再次失败……**无限循环，日志刷屏、CPU 打满**。这是最容易踩的坑。
- **为什么进死信而不是直接丢弃**：丢弃等于消息人间蒸发，没人知道它存在过；死信队列至少留下尸体，可以人工重放或排查。

**不这么做会怎样**：自动 ACK + 消费端崩溃 = 静默丢单；`requeue = true` = 无限重投死循环（第 09 章的补偿表就是为了替代这条路）。

**代价要承认**：现在没有本地重试，一次异常就进死信，需要人工介入。这是刻意的取舍——**宁可多一次人工，不要多一次死循环**。

### 6.9 生产者可靠性：Confirm + Return 缺一不可

**做什么**：确保"消息真的到达了队列"，而不只是"我以为发出去了"。

**怎么做**：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # 到达交换机后回调
    publisher-returns: true              # 无法路由时退回
    template:
      mandatory: true                    # 无法路由时必须退回，不能静默丢弃
```

**为什么**：

| 机制 | 解决什么 | 失败表现 |
|---|---|---|
| **Confirm** | 消息有没有到达**交换机** | Broker 回 `nack` |
| **Return** | 到了交换机，有没有**路由到队列** | 消息被退回给生产者 |
| **mandatory** | 无法路由时**必须**退回，而不是静默丢弃 | 没有它，Return 根本不会触发 |

**两个都要**：只开 Confirm，消息到了交换机但路由键写错、没绑定队列，Broker 照样 `ack`——你以为成功了，其实消息进了黑洞。项目里 `mandatory: true` 是让 Return 真正生效的开关。

**不这么做会怎样**：路由键拼错一个字母（`seckill.order.creat`），消息静默消失，接口还返回"排队中"，用户永远等不到结果，而且日志里干干净净。

### 6.10 结果查询：先查 Redis，再落 DB

**做什么**：给前端一个"这批货到底成没成"的接口。

**怎么做**：

```java
long userId = StpUtil.getLoginIdAsLong();
String redisKey = RedisKeyConstants.SECKILL_ORDER_STATUS_PREFIX + userId + ":" + orderNo;
String orderStatus = stringRedisTemplate.opsForValue().get(redisKey);

// PROCESSING / SECKILL_FAILED 直接返回，不再查库
// 其他状态（已支付、已取消等）再回源 DB
```

**为什么**：

- 消费端处理完会写 Redis 状态，**查 Redis 是微秒级**，能扛住前端每秒一次的轮询。
- 只有 Redis 里没有（过期、异常）才落 DB，把数据库的读压力压到最低。
- 状态 key 带 TTL（`SECKILL_ORDER_STATUS_TTL_MINUTES`），避免 Redis 无限增长。

**不这么做会怎样**：前端 1 秒轮询一次，10 万用户就是 10 万 QPS 全打在数据库上——**消峰消了个寂寞，查询把数据库又打死了**。

---

### 6.11 SSE：把"轮询"换成"我通知你"

**做什么**：客户端建一条长连接，服务端处理完主动推结果。

**怎么做**：

```java
// 每个连接用 userId:orderNo 作为唯一标识
private final Map<String, SseEmitter> emitterMap = new ConcurrentHashMap<>();

SseEmitter emitter = new SseEmitter(60_000L);   // 60 秒超时
emitterMap.put(key, emitter);

// 三种结束方式都要清理，漏一个就是内存泄漏
emitter.onCompletion(() -> emitterMap.remove(key));
emitter.onTimeout(() -> emitterMap.remove(key));
emitter.onError(e -> emitterMap.remove(key));
```

推送时**先 remove 再 send**，保证一条连接只推一次。

**为什么**：

- **为什么用 `ConcurrentHashMap`**：订阅发生在 Tomcat 线程，推送发生在 MQ 消费线程，**跨线程访问必须线程安全**，普通 `HashMap` 会丢连接甚至死循环。
- **为什么三个回调都要清理**：用户关页面（completion）、服务端超时（timeout）、网络异常（error）走的是不同回调，漏一个就是一批"僵尸连接"。
- **为什么设 60 秒超时**：连接不能无限挂。用户如果 60 秒还没拿到结果，说明系统已经异常，继续挂着只是占资源。
- **为什么推送前先 remove**：避免"同一个结果推两次"和"连接被清理两次"。

**不这么做会怎样**：内存里堆满已断开的 `SseEmitter`，最终 OOM——**而且这个问题在压测时不一定暴露，只会在线上慢慢发酵**。

## 七、常见坑

- `@RabbitListener` 默认单线程消费 → 消费能力远低于生产速度，队列堆积
- 消费端抛异常且 `requeue=true` → 无限重投，CPU 打满（本项目用 `requeue=false` + 死信）
- 只开 Confirm 不开 Return/mandatory → 路由失败静默丢消息
- 消息体用 JDK 序列化 → 管理台乱码，跨语言困难（用 `Jackson2JsonMessageConverter`）
- 消费者未做幂等 → 至少一次投递导致重复订单
- `prefetch` 设得过大或为 0 → 单个消费者囤积，其他消费者空闲
- 先发消息后写 PROCESSING 状态 → 状态被消费端覆盖，用户永远看到"处理中"
- 异步化后前端一直转圈 → 必须配套结果查询/推送
- SSE 只清理了 `onCompletion`，漏掉 `onTimeout` / `onError` → 连接泄漏
- 秒杀结果缓存没有 TTL → Redis 内存持续增长

## 八、面试追问

### 8.0 当时到底卡在哪

**卡点一：QPS 卡在 50，加机器也没用。**

加了 Lua 预扣之后，Redis 那一段很快，但下单接口还是慢——因为**扣库存、写订单、开事务仍然在请求线程里同步做**。瓶颈不在代码写得丑，而在于：一个 HTTP 请求的生命周期，被一个数据库事务的长度绑死了。

**卡点二：异步化之后，用户不知道该干嘛。**

改成发 MQ 后接口是秒回了，但用户点完"立即抢购"，页面只能一直转圈。他不知道自己是抢到了还是没抢到——**技术上异步了，体验上断片了**。

**卡点三：消费者单线程，队列堆到几万条。**

`@RabbitListener` 默认一个消费者、一次处理一条。生产端每秒几千条，消费端每秒几十条，队列像堵住的下水道一样往上灌。

**卡点四：消费端一抛异常，消息就无限重投。**

订单落库时偶发死锁抛了异常，消息被反复投回来，日志刷屏、CPU 打满，同一笔订单在数据库里被反复尝试插入。

### 8.1 为什么最后引入了这些技术

**消息队列**，引入它是为了：

- 不是让请求变快，而是让请求**排队**；
- 不是让数据库变强，而是让数据库**匀速**；
- 不是把流量消灭，而是把**尖峰摊平**——**山还是那座山，只是从悬崖变成了缓坡**。

**手动 ACK + 重试 + 死信队列**，引入它们是为了：

- 不是不信任 MQ，而是不信任"网络一定通、消费一定成"；
- 不是把失败藏起来，而是把失败**收容**起来；
- 不是保证"消息一定被处理"，而是保证"没被处理的消息一定有人知道"。

**SSE 结果推送**，引入它是为了：

- 不是炫技，而是为了让"异步"对用户**可见**；
- 不是替代轮询，而是把"每秒问一次"变成"有结果我叫你"；
- 不是让系统更快，而是让等待**不那么难熬**。

### 8.2 面试追问（附参考答案）

**Q1：削峰填谷的本质是什么？为什么能提升系统吞吐？**

A：本质是**把"瞬时并发"转换成"持续排队"**。

不用 MQ 时，10000 个请求同时到达，服务器和数据库必须按 10000 的规格去扛，扛不住就雪崩；用了 MQ，这 10000 个请求变成 10000 条消息，消费端按自己的节奏（比如每秒 500 条）慢慢处理。

吞吐提升的真正原因不是"MQ 更快"，而是：
- **数据库的事务被拉长成匀速的小事务**，不再有锁竞争的高峰；
- **请求线程被解放**，HTTP 层只负责"收下并回执"，不再等待落库；
- **系统按"平均能力"设计，而不是按"峰值能力"设计**——成本差一个数量级。

代价也要说清楚：**一致性从"强"变成了"最终"，复杂度从"一个事务"变成了"一条链路"**。

**Q2：MQ 消息丢失可能发生在哪三个环节？分别怎么解决？**

A：
1. **生产者 → Broker**：网络抖动、Broker 未落盘。
   → 开启 `publisher-confirm-type: correlated`（确认到达交换机）+ `publisher-returns: true` + `mandatory: true`（确认路由到队列），失败落补偿表。
2. **Broker 自身**：内存里的消息还没落盘就宕机。
   → 交换机/队列/消息都设持久化（`durable=true` + `deliveryMode=PERSISTENT`），必要时用镜像队列或仲裁队列。
3. **Broker → 消费者**：消费者拿到消息后、处理完之前宕机。
   → 关闭自动 ACK，改成**手动 ACK**，处理成功才 `basicAck`；失败 `basicNack(requeue=false)` 进死信队列。

记忆口诀：**发得出、存得住、收得下**。

**Q3：`prefetch` 和 `concurrency` 分别控制什么？**

A：
- **`prefetch`（预取数量）**：控制**一个消费者最多囤多少条未 ACK 的消息**。设大了，一条消息处理慢会把后面的堵在这一个消费者身上；设小了，消费者频繁往返拉取，吞吐上不去。项目里配的是 5。
- **`concurrency`（并发消费者数）**：控制**同时有多少个消费者在消费**。它决定的是"并行度"，不是"囤货量"。项目里在注解上写的是 `5-10`。

关系可以这么理解：`concurrency` 是开了几个窗口，`prefetch` 是每个窗口一次能拿几张单。窗口太少会排队，单次拿太多会让某个窗口忙死、别的窗口闲着。

**Q4：为什么消费端必须做幂等？不做会怎样？**

A：因为 MQ 的投递语义是**至少一次（at least once）**，不是"恰好一次"。网络超时、ACK 丢失、消费者重启，都会导致同一条消息被投递多次。

不做幂等的后果直接体现在业务上：
- 一笔订单被创建两次，用户被扣两次钱；
- 库存被多扣，明明还有货却显示售罄；
- 补偿逻辑被执行两次，库存越补越多。

项目里的兜底是**唯一索引**：`t_seckill_order` 上 `order_no` 唯一，重复插入直接抛 `DuplicateKeyException`，捕获后当作"已处理"幂等返回。这是最可靠的一种——**不依赖代码逻辑，依赖数据库约束**。

**Q5：异步下单用户怎么知道结果？轮询和 SSE 哪个好？**

A：
- **轮询**：前端按固定间隔（比如 1 秒）调 `/result` 接口查状态。实现简单、兼容性好，但**绝大多数请求是无效的**（还没处理完），而且延迟取决于轮询间隔。
- **SSE（Server-Sent Events）**：客户端建一条长连接，服务端处理完主动推。用户感知是"秒出结果"，服务端也不用被反复查询。

项目里两种都实现了：`/seckill/order/result` 查一次，`/seckill/order/result/subscribe` 用 SSE 订阅。

选择建议：**能用推送就用推送，推送不可用时用轮询兜底**。但要注意 SSE 的代价——每条连接占一个 Tomcat 线程或一个异步上下文，连接数一多，服务端的连接管理本身就成了新问题。

**Q6：RabbitMQ 和 RocketMQ / Kafka 在秒杀场景怎么选？**

A：
- **RabbitMQ**：延迟低（毫秒级）、路由灵活（Exchange/Queue/Binding 组合多）、管理界面好用。适合**业务消息**——订单、通知、补偿这类"每条消息都很重要"的场景。缺点是吞吐量相比 Kafka 低一个量级。
- **RocketMQ**：吞吐高、支持事务消息、支持顺序消息、有延迟队列。国内电商场景用得多，**秒杀这类需要"事务消息 + 削峰"的场景很合适**。
- **Kafka**：吞吐最高，为日志/流处理而生。**不支持延迟消息、不支持逐条 ACK、分区内有序**，做业务消息要额外补很多东西。

秒杀场景的真实选择逻辑：**先看团队会不会运维，再看吞吐够不够，最后才看功能**。教程用 RabbitMQ 是因为它的 Confirm/Return/手动 ACK/死信这套机制最完整、最适合讲清楚"可靠性"这件事；真上量到十万级，才需要考虑 RocketMQ 或 Kafka。
