## 二、削峰填谷原理

```
同步模式（阶段一/二）：
10000 请求 ──┐
             ├──► 业务线程 ──► DB（被打爆，大量超时）
             ┘    （线程池瞬间耗尽）

异步模式（阶段三）：
10000 请求 ──► Redis 校验 ──► MQ（消息堆积，但接口立刻返回"排队中"）
                                    │
                       消费者按自己的节奏消费（平滑速率）──► DB
```

**关键收益**：接口响应时间从"取决于 DB 落库速度"变成"取决于入队速度"，
瞬时流量被 MQ 吸收，DB 只承受消费者可控速率的写入。

> **代价**：用户体验从"同步返回结果"变成"异步等待结果"，所以必须配套结果查询/推送。

## 三、RabbitMQ 关键配置

```yaml
spring:
  rabbitmq:
    host: 127.0.0.1
    port: 5672
    username: admin
    password: admin123
    publisher-confirm-type: correlated   # 生产者确认
    publisher-returns: true              # 路由失败回调
    listener:
      simple:
        acknowledge-mode: manual         # 手动 ACK
        prefetch: 10                     # 每个消费者预取数量（削峰关键）
        concurrency: 5                   # 并发消费者数量
        max-concurrency: 10
        retry:
          enabled: true
```

### 参数含义（面试常问）

| 参数 | 作用 | 调优方向 |
|---|---|---|
| `prefetch` | 消费者一次最多预取多少条未 ACK 消息 | 调小更平滑防堆积单消费者，调大吞吐高但内存占用大 |
| `concurrency` | 每个监听器的并发消费线程数 | 提高消费能力，但不能超过 DB 承载 |
| `acknowledge-mode: manual` | 手动 ACK，业务成功才确认 | 必须配合幂等 |
| DLX | 消费失败进死信队列人工处理 | 防消息丢失黑洞 |

### 死信产生的三种情况

1. 消息被 `basic.nack/reject` 且 `requeue=false`
2. 消息 TTL 过期
3. 队列达到最大长度

## 四、异步下单链路（核心流程）

```
1. 用户点击秒杀
2. 接口做前置校验（登录、活动时间、限购、库存预判）
3. 生成全局唯一订单号（雪花/Redis 自增）
4. 发送 MQ 消息（携带 userId、goodsId、订单号）
   ├─ 发送成功 → 返回"排队中"，前端开始轮询/SSE 等待
   └─ 发送失败 → 回补库存 + 返回失败（这是第 7 章的重点）
5. 消费者：
   a. 幂等判断（订单号/唯一索引，已处理则直接 ACK）
   b. 扣减 DB 库存（`UPDATE ... WHERE stock > 0`）
   c. 创建订单（唯一索引兜底）
   d. 更新 Redis 中的秒杀结果
   e. 成功后手动 ACK；失败进死信队列
6. 前端通过轮询 `/seckill/result` 或 SSE 拿到最终结果
```

## 六、验收标准

| 指标 | 要求 |
|---|---|
| 下单接口响应时间 | 稳定在毫秒级（不随 DB 压力波动） |
| 消息不丢 | 生产端 Confirm 全部成功；消费端无消息黑洞 |
| 消费可观测 | 管理台能看到队列堆积被平稳消费完 |
| 结果可达 | 前端能通过轮询或 SSE 拿到最终结果 |
| 幂等 | 重复投递同一消息不会产生重复订单 |

## 七、常见坑

- `@RabbitListener` 默认单线程消费 → 消费能力远低于生产速度，队列堆积
- 消费端抛异常默认无限重投 → 死循环打爆日志与 CPU（需配 retry + DLX）
- 消息体用 JDK 序列化，可读性差且跨语言困难（用 `Jackson2JsonMessageConverter`）
- 消费者未做幂等 → MQ 至少一次投递导致重复订单
- `prefetch` 设得过大 → 单个消费者囤积大量消息，其他消费者空闲
- 异步化后前端一直转圈 → 必须配套结果查询/推送
- 秒杀结果缓存没有 TTL，Redis 内存增长

## 八、面试追问

### 8.0 当时到底卡在哪

**卡点一：QPS 卡在 50，加机器也没用。**

加了 Lua 预扣之后，Redis 那一段很快，但下单接口还是慢——因为**扣库存、写订单、开事务仍然在请求线程里同步做**。瓶颈不在代码写得丑，而在于：一个 HTTP 请求的生命周期，被一个数据库事务的长度绑死了。

**卡点二：异步化之后，用户不知道该干嘛。**

改成发 MQ 后接口是秒回了，但用户点完"立即抢购"，页面只能一直转圈。他不知道自己是抢到了还是没抢到——**技术上异步了，体验上断片了**。

**卡点三：消费者单线程，队列堆到几万条。**

`@RabbitListener` 默认一个消费者、一次处理一条。生产端每秒几千条，消费端每秒几十条，队列像堵住的下水道一样往上灌。

**卡点四：消费端一抛异常，消息就无限重投。**

订单落库时偶发死锁抛了异常，消息被反复投回来，日志刷屏、CPU 打满，同一笔订单在数据库里被反复尝试插入。

### 8.1 为什么最后引入了这些技术

**消息队列**，引入它是为了：

- 不是让请求变快，而是让请求**排队**；
- 不是让数据库变强，而是让数据库**匀速**；
- 不是把流量消灭，而是把**尖峰摊平**——**山还是那座山，只是从悬崖变成了缓坡**。

**手动 ACK + 重试 + 死信队列**，引入它们是为了：

- 不是不信任 MQ，而是不信任"网络一定通、消费一定成"；
- 不是把失败藏起来，而是把失败**收容**起来；
- 不是保证"消息一定被处理"，而是保证"没被处理的消息一定有人知道"。

**SSE 结果推送**，引入它是为了：

- 不是炫技，而是为了让"异步"对用户**可见**；
- 不是替代轮询，而是把"每秒问一次"变成"有结果我叫你"；
- 不是让系统更快，而是让等待**不那么难熬**。

### 8.2 面试追问（附参考答案）

**Q1：削峰填谷的本质是什么？为什么能提升系统吞吐？**

A：本质是**把"瞬时并发"转换成"持续排队"**。

不用 MQ 时，10000 个请求同时到达，服务器和数据库必须按 10000 的规格去扛，扛不住就雪崩；用了 MQ，这 10000 个请求变成 10000 条消息，消费端按自己的节奏（比如每秒 500 条）慢慢处理。

吞吐提升的真正原因不是"MQ 更快"，而是：
- **数据库的事务被拉长成匀速的小事务**，不再有锁竞争的高峰；
- **请求线程被解放**，HTTP 层只负责"收下并回执"，不再等待落库；
- **系统按"平均能力"设计，而不是按"峰值能力"设计**——成本差一个数量级。

代价也要说清楚：**一致性从"强"变成了"最终"，复杂度从"一个事务"变成了"一条链路"**。

**Q2：MQ 消息丢失可能发生在哪三个环节？分别怎么解决？**

A：
1. **生产者 → Broker**：网络抖动、Broker 未落盘。
   → 开启 `publisher-confirm-type: correlated`（确认到达交换机）+ `publisher-returns: true`（确认路由到队列），失败落补偿表。
2. **Broker 自身**：内存里的消息还没落盘就宕机。
   → 交换机/队列/消息都设持久化（`durable=true` + `deliveryMode=PERSISTENT`），必要时用镜像队列或仲裁队列。
3. **Broker → 消费者**：消费者拿到消息后、处理完之前宕机。
   → 关闭自动 ACK，改成**手动 ACK**，处理成功才 `basicAck`；失败 `basicNack` 进重试或死信队列。

记忆口诀：**发得出、存得住、收得下**。

**Q3：`prefetch` 和 `concurrency` 分别控制什么？**

A：
- **`prefetch`（预取数量）**：控制**一个消费者最多囤多少条未 ACK 的消息**。设大了，一条消息处理慢会把后面的堵在这一个消费者身上；设小了，消费者频繁往返拉取，吞吐上不去。项目里配的是 5。
- **`concurrency`（并发消费者数）**：控制**同时有多少个消费者在消费**。它决定的是"并行度"，不是"囤货量"。

关系可以这么理解：`concurrency` 是开了几个窗口，`prefetch` 是每个窗口一次能拿几张单。窗口太少会排队，单次拿太多会让某个窗口忙死、别的窗口闲着。

**Q4：为什么消费端必须做幂等？不做会怎样？**

A：因为 MQ 的投递语义是**至少一次（at least once）**，不是"恰好一次"。网络超时、ACK 丢失、消费者重启，都会导致同一条消息被投递多次。

不做幂等的后果直接体现在业务上：
- 一笔订单被创建两次，用户被扣两次钱；
- 库存被多扣，明明还有货却显示售罄；
- 补偿逻辑被执行两次，库存越补越多。

项目里的兜底是**唯一索引**：`t_seckill_order` 上 `order_no` 唯一，重复插入直接抛 `DuplicateKeyException`，捕获后当作"已处理"幂等返回。这是最可靠的一种——**不依赖代码逻辑，依赖数据库约束**。

**Q5：异步下单用户怎么知道结果？轮询和 SSE 哪个好？**

A：
- **轮询**：前端按固定间隔（比如 1 秒）调 `/result` 接口查状态。实现简单、兼容性好，但**绝大多数请求是无效的**（还没处理完），而且延迟取决于轮询间隔。
- **SSE（Server-Sent Events）**：客户端建一条长连接，服务端处理完主动推。用户感知是"秒出结果"，服务端也不用被反复查询。

项目里两种都实现了：`/seckill/order/result` 查一次，`/seckill/order/result/subscribe` 用 SSE 订阅。

选择建议：**能用推送就用推送，推送不可用时用轮询兜底**。但要注意 SSE 的代价——每条连接占一个 Tomcat 线程或一个异步上下文，连接数一多，服务端的连接管理本身就成了新问题。

**Q6：RabbitMQ 和 RocketMQ / Kafka 在秒杀场景怎么选？**

A：
- **RabbitMQ**：延迟低（毫秒级）、路由灵活（Exchange/Queue/Binding 组合多）、管理界面好用。适合**业务消息**——订单、通知、补偿这类"每条消息都很重要"的场景。缺点是吞吐量相比 Kafka 低一个量级。
- **RocketMQ**：吞吐高、支持事务消息、支持顺序消息、有延迟队列。国内电商场景用得多，**秒杀这类需要"事务消息 + 削峰"的场景很合适**。
- **Kafka**：吞吐最高，为日志/流处理而生。**不支持延迟消息、不支持逐条 ACK、分区内有序**，做业务消息要额外补很多东西。

秒杀场景的真实选择逻辑：**先看团队会不会运维，再看吞吐够不够，最后才看功能**。教程用 RabbitMQ 是因为它的 Confirm/Return/手动 ACK/死信这套机制最完整、最适合讲清楚"可靠性"这件事；真上量到十万级，才需要考虑 RocketMQ 或 Kafka。
