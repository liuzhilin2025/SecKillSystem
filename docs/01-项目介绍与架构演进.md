# 01 · 项目介绍与架构演进

> 建议用时：0.5 天 ｜ 前置：无 ｜ 性质：整体认知，先读这一篇再动手

## 学习目标

1. 说清楚秒杀系统为什么是"高并发"的经典练兵场。
2. 记住四阶段架构演进路线，知道**每一步是为了解决什么问题**。
3. 建立"问题驱动 + 压测验证"的工程方法论。

---

## 一、秒杀系统的七个核心难题

| # | 难题 | 典型现象 | 对应解决方案（本专栏路径） |
|---|---|---|---|
| 1 | 瞬时高并发 | 服务/DB 连接被打满，大量超时 | 缓存 + MQ 削峰 + 限流 |
| 2 | 库存超卖 | 卖出去 120 件但只有 100 件库存 | SQL 条件扣减 / 乐观锁 / Redis Lua |
| 3 | 重复下单 | 一人抢到多件 | 唯一索引 + 应用层锁 + Lua 一人一单 |
| 4 | 黄牛刷单 | 脚本高频请求、多账号 | 接口限流 + 秒杀令牌 + 行为验证码 |
| 5 | 服务雪崩 | 下游变慢导致上游线程耗尽 | 线程池隔离、熔断降级（Sentinel） |
| 6 | 数据一致性 | Redis 扣了库存，DB 落库失败 | 库存回补 + 失败补偿表 + 定时补偿 |
| 7 | 可扩展性 | 单机扛不住，无法水平扩容 | 无状态化 + 微服务拆分 + 分布式锁 |

## 二、四阶段架构演进

```
阶段一：浏览器 ──► 单体应用 ──► MySQL            ≈ 50 QPS
                     （暴露超卖、重复下单）

阶段二：浏览器 ──► 单体应用 ──► Redis(缓存) ──► MySQL
                     （读性能优化，穿透/击穿/雪崩治理）

阶段三：浏览器 ──► 单体应用 ──► Redis ──► MQ ──► 消费者 ──► MySQL
                     （异步下单、削峰填谷）

阶段四：浏览器 ──► Gateway ──► [秒杀服务 | 订单服务 | 商品服务 | 支付服务]
                                    Nacos / Sentinel / OpenFeign      30000+ QPS
```

### 各阶段关键动作

**阶段一 · 建立基线**
- 直连数据库实现秒杀下单
- 用 JMeter 压出 `100 用户抢 10 件 → 超卖`、`同一用户重复下单`
- 用 SQL 条件扣减 / 乐观锁解决超卖，用唯一索引 + 应用层锁解决重复下单
- 得到"朴素实现"的性能基线（≈50 QPS）——**这个数字后面每一步都在打它**

**阶段二 · 读性能**
- 缓存 Key 设计规范、商品列表/详情加缓存
- 缓存一致性（先更新 DB 再删缓存）、缓存预热、动态 TTL
- 缓存穿透治理：空值策略 → Bloom 布隆过滤器
- 本地缓存 Caffeine 组成多级缓存

**阶段三 · 写削峰**
- 下单请求先写 Redis、再发 MQ，消费者异步落库
- MQ 可靠性：生产者 Confirm/Return、消费者手动 ACK + 死信队列
- 秒杀结果查询接口 + SSE 实时推送

**阶段四 · 治理与拆分**
- 单体拆微服务，Nacos 注册配置、Gateway 网关统一入口
- Sentinel 限流熔断降级、OpenFeign 声明式调用
- 页面静态化 + CDN、支付宝沙箱支付闭环

## 五、学习方法论（贯穿全项目）

> **问题驱动 → 压测暴露 → 方案对比 → 编码实现 → 复测验收**

1. 每章先问"这一章解决什么问题"，再动手写代码。
2. 每章必须有一次 JMeter 压测（前后对比数据）。
3. 每章产出一份笔记：现象 / 原因 / 方案 / 选择 / 数据。
4. 把面试高频问题整理进 [进度追踪表](./进度追踪表.md) 的"面试追问"列。
