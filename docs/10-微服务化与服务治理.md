# 10 · 微服务化与服务治理（阶段四：30000+ QPS）

> 建议用时：5~6 天 ｜ 前置：[09-MQ消息可靠性](./09-MQ消息可靠性.md)
> 阶段目标：从单体走向微服务，可水平扩展、可治理、可观测，冲击 **30000+ QPS**

## 学习目标

1. 说清楚为什么单体架构最终会成为瓶颈，以及拆分的正确时机与边界。
2. 用 Nacos 做注册中心 + 配置中心，Gateway 做统一入口与限流。
3. 用 Sentinel 做熔断、限流、降级，用 OpenFeign 做声明式调用。
4. 掌握页面静态化 + CDN 的动静分离思路与支付宝沙箱支付闭环。
5. 完成全链路压测，达成 30000+ QPS 目标。

---

## 一、为什么需要微服务化

| 单体瓶颈 | 说明 |
|---|---|
| 无法按模块扩容 | 秒杀服务是热点，但订单/支付模块不热，只能整体扩容，浪费资源 |
| 故障隔离差 | 一个模块的慢查询/内存泄漏会拖垮整个应用 |
| 发布耦合 | 改一个接口要全量发布，风险大 |
| 技术栈统一 | 无法针对不同模块选择合适的技术 |

> **重要原则：先优化单体，再拆微服务。** 拆分带来的是分布式复杂度（网络、事务、链路追踪），
> 如果单体的缓存/MQ/Lua 优化没做完就拆，只是把问题分散到更多节点上。

## 二、服务拆分建议

```
                    ┌─────────────┐
   浏览器/App ──────►│  Gateway    │  ← 统一路由、鉴权、限流、跨域
                    └──────┬──────┘
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
 ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
 │ 秒杀服务     │   │ 商品服务     │   │ 订单服务     │
 │ seckill     │   │ goods       │   │ order       │
 └──────┬──────┘   └─────────────┘   └──────┬──────┘
        │  Feign                              │
        └──────────────►┌─────────────┐◄──────┘
                        │ 支付服务     │
                        │ pay         │
                        └─────────────┘
                 Nacos（注册 + 配置）  Sentinel（熔断限流）
```

| 服务 | 职责 |
|---|---|
| `gateway` | 统一入口、路由转发、JWT/Sa-Token 统一鉴权、全局限流 |
| `seckill-service` | 秒杀列表/详情/令牌/下单（最核心、最先扩容） |
| `goods-service` | 商品基础信息、库存（可独立缓存） |
| `order-service` | 订单落库、订单查询、超时未支付关单 |
| `pay-service` | 支付、退款、异步回调 |

## 三、核心组件用法

### Nacos（注册中心 + 配置中心）

- 服务启动自动注册，网关按服务名路由，支持实例上下线
- 配置中心实现**配置热更新**（`@RefreshScope`），秒杀活动开关无需重启
- 秒杀场景实用技巧：用 Nacos 配置**秒杀开关**，活动异常时一键降级

### Gateway（网关）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: seckill
          uri: lb://seckill-service
          predicates:
            - Path=/api/seckill/**
          filters:
            - StripPrefix=2
            - name: RequestRateLimiter     # 基于 Redis 的网关层限流
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
```

> **分层限流设计**：网关层（总入口）→ 应用层（`@RateLimiter`）→ 令牌大闸 → 线程池泄洪。

### Sentinel（熔断降级）

| 规则 | 用途 |
|---|---|
| 流控（QPS/线程数） | 保护自身 |
| 熔断（慢调用比例/异常比例） | 保护调用方，避免雪崩 |
| 热点参数限流 | 针对单个爆款商品限流 |
| 系统自适应保护 | 按 Load / CPU 自动限流 |

配合 `@SentinelResource(value = "seckillOrder", blockHandler = "...", fallback = "...")` 使用。

### OpenFeign（服务调用）

```java
@FeignClient(name = "goods-service", fallbackFactory = GoodsClientFallback.class)
public interface GoodsClient {
    @GetMapping("/goods/{id}")
    Result<GoodsVO> getGoods(@PathVariable Long id);
}
```

> 必须配置 **超时时间 + 降级（fallback）**，秒杀链路中下游不可用时要能快速失败。

| 手段 | 说明 |
|---|---|

## 八、常见坑

- 拆分过早 / 拆得太细：分布式事务、链路变长、运维成本飙升
- Feign 未设超时 → 下游慢调用拖垮上游线程池（雪崩）
- Sentinel 规则未持久化 → 重启后规则丢失（需接 Nacos 持久化）
- 网关限流阈值设得比后端承载能力大 → 限流形同虚设
- 服务间调用没有传递用户上下文 → 鉴权失效
- 只加机器不看瓶颈：DB/Redis 先成瓶颈，加服务节点无效
- 分布式事务乱用 Seata，秒杀场景更应该用**最终一致（补偿）**

## 九、面试追问

> **先说明一点**：这一章目前只在设计层面推演，项目代码仍是单体多模块结构（没有 Nacos / Gateway / Sentinel 的实现）。下面写的"卡点"，是在单机上把服务拆开之后**必然会遇到**的问题，不是已经跑通的结论。

### 会卡在哪（拆开之后必然出现的问题）

**卡点一：用户登录态在服务之间丢了。**

单体里 `StpUtil.getLoginIdAsLong()` 随手就能取，因为 Token 校验和业务在同一个进程。拆成网关 + 订单服务之后，请求到了订单服务，`Sa-Token` 的拦截器发现拿不到 Token——因为 Token 在网关那边被消费掉了，或者 Feign 调用时压根没把 Header 带过去。

**卡点二：网关限流阈值拍得比后端能力大。**

网关配了"每秒放行 5000 个请求"，觉得很有安全感。但订单服务后面的 MySQL 只扛得住 500 QPS。结果网关形同虚设，请求全部穿过去，数据库照样被打挂。

**卡点三：Sentinel 规则配完，重启就没了。**

在控制台点得很爽，服务一重启，流控规则全丢。原因是没有接 Nacos 做规则持久化——**规则也是配置，配置不能只活在内置内存里。**

**卡点四：Feign 没设超时，一个慢服务拖垮整条链。**

订单服务调库存服务，库存服务因为 GC 卡了 5 秒，订单服务的线程全被占住，紧接着网关的线程也被占住——**一个下游的抖动，顺着调用链一路上溯，最后全线雪崩。**

### 为什么最后是这些技术

**网关**，引入它是为了：

- 不是多一道转发，而是把**认证、限流、日志、灰度**这些横切关注点从每个服务里抽出来；
- 不是让请求多走一跳，而是让**每个服务都不必重复实现一遍**；
- 不是替代应用层防护，而是**在离用户最近的地方先挡一层**。

**Sentinel**，引入它是为了：

- 不是把流量拦住，而是把流量**限制在系统能承受的范围内**；
- 不是让服务不挂，而是让服务**挂得慢一点、挂得局部一点**；
- 不是技术上的完美方案，而是**工程上的止损方案**——先保住核心链路，再谈其他。

**最终一致（补偿）而不是强一致（分布式事务）**，选它是为了：

- 不是不想一致，而是**秒杀场景承受不起强一致的代价**；
- 不是放弃正确性，而是把"正确"拆成"最终会正确"；
- 不是为了省事，而是因为**库存扣减的正确性早就在 Redis + 唯一索引那里守住了**，下游只需要"迟早一致"。

### 面试追问（附参考答案）

**Q1：什么时候该拆微服务？拆分的依据是什么？**

A：**拆分的依据不是"业务有几个模块"，而是"谁需要独立变化、独立扩容"。**

该拆的信号：
1. **团队规模**：一个模块超过 8~10 人协作，代码冲突和发布排队成为主要成本；
2. **扩缩容诉求不同**：秒杀下单服务和后台管理服务的流量差 100 倍，绑在一起必须按高的配置资源；
3. **故障隔离诉求**：一个非核心功能（如推荐）拖垮核心下单，说明该隔离；
4. **技术栈差异**：某个模块必须用不同的语言或存储。

不该拆的信号：
- 流量还没到单体的上限（先压测，别拍脑袋）；
- 团队只有三五个人，拆完运维成本比开发成本还高；
- 业务边界还没稳定，今天拆明天合。

一句话：**微服务是组织架构的映射，不是技术水平的证明。**

**Q2：秒杀链路需要强一致还是最终一致？为什么？**

A：**关键节点强一致，全链路最终一致。**

- **强一致的部分**：Redis 里的库存扣减和"一人一单"标记。这里必须原子，否则就是超卖和重复下单——所以用 Lua。
- **最终一致的部分**：Redis 预扣成功 → MQ → DB 落库 → 订单生成。这条链路上任何一步失败，都靠**补偿**回到一致状态，而不是靠分布式事务。

为什么不用强一致（Seata 那套）：
1. **性能代价太大**：分布式事务要多次网络往返 + 全局锁，秒杀场景下这是致命的；
2. **可用性下降**：任何一个参与方不可用，全局事务就卡住；
3. **没那么必要**：库存的正确性在 Redis 那一层已经守住了，DB 落库失败只是"少卖"，可以补偿，不会"超卖"。

一句话：**能靠补偿解决的，别用事务锁死；能在一个原子操作里解决的，别拆成两个服务。**

**Q3：网关层限流和应用层限流的区别？**

A：

| | 网关层限流 | 应用层限流 |
|---|---|---|
| 位置 | 流量入口，所有服务之前 | 具体服务内部 |
| 粒度 | 路由级、IP 级、用户级（粗） | 接口级、方法级、业务维度（细） |
| 能力 | 挡掉大部分无差别流量 | 按业务语义精准控制（如"每用户每商品 5 次"） |
| 优点 | 统一、成本低、保护所有下游 | 能感知业务，策略更灵活 |
| 缺点 | 不懂业务，容易误伤 | 每加一个服务都要实现一遍 |

正确姿势是**两层配合**：网关先做粗粒度削峰（把 10 万降到 1 万），应用层再做精细控制（每用户 5 次、每 IP 50 次）。

注意：**网关的阈值必须小于后端真实承载能力**，否则就是自我安慰。

**Q4：Sentinel 的熔断和降级有什么区别？**

A：
- **熔断（Circuit Breaker）**：是一种**自动的状态切换**。当某个下游的错误率/慢调用比例超过阈值，熔断器从"关闭"变成"打开"，后续请求**直接快速失败**，不再调用下游；过一段时间进入"半开"，放少量请求试探，成功就恢复。
  - 关键词：**自动、基于指标、保护调用方**。
- **降级（Degrade）**：是一种**业务兜底策略**。功能不可用时返回一个预设的默认值或友好提示（如"当前人数过多"），保证主流程不中断。
  - 关键词：**人工预设、业务语义、保证体验**。

关系：**熔断是触发条件，降级是处理结果**。熔断器打开之后，通常就走降级逻辑（返回兜底数据），而不是把异常直接抛给用户。

**Q5：如何在微服务间传递用户登录信息？**

A：三种方式，从简到繁：

1. **透传 Token（最常用）**：网关校验完 Token 后，把 `userId` 放进请求头（如 `X-User-Id`），Feign 调用时通过 `RequestInterceptor` 把这个头继续往下传。下游服务信任网关注入的头，不再重复校验。
   - 关键点：**内网服务必须只允许网关访问**，否则外部可以直接伪造 `X-User-Id`。
2. **透传原始 Token**：Feign 拦截器把 `Authorization` 头带上，下游各自用 Sa-Token 校验。安全性好，但每次都要查一次 Redis。
3. **内部签名**：网关用密钥对 `userId + timestamp` 签名，下游验签。防伪造最强，实现最复杂。

项目现在还是单体，`SaTokenConfig` 是白名单式配置；真拆服务时，**第一件要做的事就是把"信任边界"画清楚**——谁能信任谁的头，必须写死在网关配置里。

**Q6：30000 QPS 是怎么算出来的？压测环境和生产环境差多少？**

A：**30000 是目标值，不是实测值**，通常按"峰值流量 ÷ 可接受的单机 QPS"倒推机器数。

真实压测要交代清楚四件事，否则数字没有意义：
1. **压测机在哪**：和应用同机（互相抢 CPU）还是独立机器，差 30% 以上；
2. **压测工具与模式**：JMeter 1000 线程 ramp=0 的瞬时尖峰，和持续稳定压测，结果完全不同；
3. **测的是哪个接口**：只测 Redis 预扣（几毫秒）和测完整下单链路（含 MQ、日志、鉴权），差一个数量级；
4. **有没有关日志**：DEBUG 全开和 INFO，QPS 能差 2~3 倍。

生产环境还会更复杂：真实网络延迟、TLS、CDN 回源、数据库真实数据量、GC 停顿、其他业务共用中间件。

所以面试时**不要只报一个数字**，要报"在什么条件下、测的哪条链路、瓶颈在哪"。**能说清楚条件的人，才真的做过压测。**

**Q7：页面静态化后，秒杀按钮的库存和状态怎么做到"看起来实时"？**

A：静态化解决的是"页面渲染"的成本，但**按钮状态必须动态获取**，思路是"静态页面 + 动态片段"：

1. **倒计时**：纯前端根据活动开始时间算，不查服务端；
2. **按钮状态（未开始/立即抢/已售罄）**：页面加载后发一个轻量接口（只查 Redis 的库存标记和活动状态），或者用 SSE 订阅状态变化；
3. **库存数字**：通常不展示精确值（会被黄牛用来判断），只展示"有货/售罄"；
4. **CDN 层的处理**：HTML 走 CDN 长缓存，动态片段用 `Cache-Control: no-cache` 或者独立接口绕过 CDN。

一句话：**页面静态化省的是"渲染"，不是"状态"。状态永远要问服务端，只是问得越轻越好。**
