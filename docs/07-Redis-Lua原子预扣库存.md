## 二、为什么 Redis Lua 是关键一步

### 阶段三之后的瓶颈

即使 MQ 削峰，消费者最终还是要执行：

```sql
UPDATE t_seckill_goods SET stock = stock - 1 WHERE id = ? AND stock > 0;
```

**同一行记录的更新会持有排他行锁，所有消费线程串行等待**。即使开了 10 个消费者，
真正能并行执行的只有 1 个（同一商品），消费速率上限被 DB 单行锁死。

### 解法：把"判断 + 扣减"整体挪到 Redis

Redis 是**单线程执行命令**的，Lua 脚本在执行期间不会被其他命令打断，
因此"读库存 → 判断 → 扣减 → 记录已购"可以作为一个**原子操作**完成。

```lua
-- KEYS[1] = seckill:stock:{goodsId}     库存
-- KEYS[2] = seckill:bought:{goodsId}    已购用户 Set
-- ARGV[1] = userId
-- ARGV[2] = 每人限购数
local stock = tonumber(redis.call('GET', KEYS[1]))
if not stock or stock <= 0 then
    return -1                                  -- 售罄
end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                                  -- 重复下单
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1                               -- 剩余库存
```

> 返回值语义要定义清晰：`>=0` 扣减成功、`-1` 售罄、`-2` 重复下单。

### 与数据库唯一索引的关系

- **Redis Lua**：拦住 99% 的无效请求，性能主力
- **DB 唯一索引 + `stock > 0`**：最后一道防线，应对 Redis 异常/回补失败等极端情况
- 两者是**互补**关系，缺一不可

## 三、数据一致性：库存回补

秒杀链路可能出现"Redis 扣减成功，但 MQ 发送失败"，此时必须回补 Redis 库存：

```java
Long result = redisTemplate.execute(seckillScript, keys, userId, limit);
if (result != null && result >= 0) {
    try {
        rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, msg);
    } catch (Exception e) {
        // 发送失败 → 回补库存 + 移除已购记录
        redisTemplate.execute(rollbackScript, keys, userId);
        throw new BizException("秒杀失败，请重试");
    }
}
```

回补脚本同样要用 Lua 保证原子性：

```lua
redis.call('INCR', KEYS[1])
redis.call('SREM', KEYS[2], ARGV[1])
return 1
```

> 更严谨的做法：**本地消息表 + 定时任务补偿**（见第 9 章），
> 因为"回补"本身也可能失败（Redis 宕机）。

## 四、售罄标记（快速失败）

```lua
-- 库存为 0 时写一个标记 key，TTL 与活动结束时间一致
redis.call('SET', 'seckill:soldout:' .. goodsId, '1', 'EX', ttl)
```

后续请求先 `EXISTS` 判断，直接返回售罄，**不再执行扣减脚本**，大幅降低 Redis 压力。

## 七、常见坑

- **Lua 脚本里用了 `KEYS` 之外动态拼 key** → Redis Cluster 下会报错（所有 key 必须通过 `KEYS[]` 传入）
- Lua 返回值类型转换错误（Redis 返回 Integer，Java 用 `Long.class`）
- 脚本内包含复杂逻辑/循环 → 阻塞 Redis 单线程，影响所有业务
- 预热与活动开始时间不同步 → 活动开始了库存还是 0
- 回补逻辑未做原子性/幂等 → 库存越补越多
- Redis 与 DB 库存双写不一致时没有对账机制
- 忘记给已购 Set 设置 TTL → 内存持续增长

## 八、面试追问

### 8.0 当时到底卡在哪

**卡点一：用 `DECR` 扣库存，照样扣出了负数。**

以为用了 `DECR` 就万事大吉，写了 `DECR` 之后再看返回值判断。问题是——**库存已经减了**。并发 100 个请求打过来，库存从 1 变成 -99，然后再去"判断"，判断得再对也晚了。

**卡点二：Lua 脚本里漏了一个 `local`，整个下单接口 500。**

脚本里写 `remainStock = redis.call('DECR', KEYS[1])`，后面又用 `tonumber(remainStock)` 做判断。本地跑没问题，一上线就报：

```
ERR user_script:61: Script attempted to access nonexistent global variable 'remainStock'
```

原因是这段代码根本没给 `remainStock` 赋过值（`DECR` 的返回值被丢掉了），而 **Redis 的 Lua 沙箱对"访问未定义的全局变量"是直接报错，不是返回 nil**。这个坑的教训是：**普通 Lua 里能容忍的写法，Redis 里不一定能容忍**。

**卡点三：库存明明还有 20，用户却被告知"已售罄"。**

排查发现是售罄标记 `seckill:soldout:1:6` 没被清掉。上一轮压测把库存抢到 0 时写入了这个标记，TTL 跟活动结束时间挂钩（这个测试活动还剩 77 天）。后来重新预热把库存恢复成 20，但**预热逻辑只 `SET` 了库存，没删标记**，于是所有请求在"快速失败"那一步就被拦下了，连 Lua 都没进去。

**卡点四：预扣成功了，MQ 发不出去，库存凭空消失。**

Redis 库存减了 1、用户标记写了，结果发 MQ 时 Broker 连不上。如果不回补，这 1 件商品就永远"锁死"在 Redis 里，DB 里也不会产生订单——**少卖，且没人知道**。

### 8.1 为什么最后引入了这些技术

**Lua 脚本**，引入它是为了：

- 不是"更快的锁"，而是**根本不需要锁**也能原子；
- 不是把代码搬到 Redis 里，而是把**临界区**搬进 Redis；
- 不是解决性能问题，而是解决正确性问题——**先把账算对，再谈算得快**。

**库存预热**，引入它是为了：

- 不是把 DB 数据抄一份，而是让下单那一刻**不碰数据库**；
- 不是缓存，而是一次**提前的对账**；
- 不是一劳永逸，而是**每轮开抢前都要重来一次**。

**预扣回补 + 幂等校验**，引入它们是为了：

- 不是所有失败都要回补，而是**只有确认失败才回补**；
- 不是补了就算完，而是补之前先确认"这笔标记还属于我吗"；
- 不是追求"一件不少卖"，而是守住"一件不多卖"——**宁可少卖，不可超卖**。

### 8.2 面试追问（附参考答案）

**Q1：Redis 为什么能保证 Lua 脚本的原子性？它是事务吗？**

A：原子性的来源是 **Redis 的单线程执行模型**——执行 Lua 脚本期间，Redis 不会插入任何其他客户端的命令，整段脚本跑完才处理下一个请求。所以脚本里的"读库存、判断、扣减、写标记"对别的请求来说是**不可分割的一瞬间**。

但它**不是事务**：
- 没有回滚。脚本执行到一半报错，**前面已经执行的写操作不会撤销**；
- 没有隔离级别，因为压根不存在并发；
- `MULTI/EXEC` 才是 Redis 意义上的事务，但它同样不支持回滚，只是把命令打包顺序执行。

一句话：**Redis 的"原子"是"不被打断"，不是"要么全成要么全败"。** 所以脚本里要么把校验放在所有写操作之前，要么自己设计好失败后的补偿。

**Q2：Redis 挂了，秒杀怎么继续？**

A：分两种态度：
- **降级到 DB 条件扣减**（`UPDATE ... WHERE stock > 0`）：能继续卖，但数据库很难扛住秒杀的流量，必须**同时开启强限流**，只放过去一小部分请求。这是"降级但不降质"。
- **直接停止秒杀**：更常见也更安全。Redis 是这条链路的强依赖，它挂了还硬撑着卖，等于把雪崩从 Redis 转移到 MySQL。

判断标准很简单：**降级后的路径必须比原来更安全，而不是换条路继续冲。** 如果降级只是把压力换个地方堆，那不叫降级，叫拆东墙补西墙。

**Q3：Redis 扣减成功但 DB 落库失败怎么办？**

A：按失败发生的阶段分三种情况：

| 阶段 | 现象 | 处理 |
|---|---|---|
| 预扣成功后、MQ 发送失败 | Redis 减了，DB 没动静 | **立即回补**：把库存加回去、删掉用户购买标记（`seckill_compensate_pre_deduct_stock.lua`） |
| 消息发出去了、消费端落库失败 | 有消息，没订单 | 消费端重试；重试耗尽进死信队列，人工处理 |
| 落库时库存已为 0（DB 扣减失败） | Redis 有货、DB 没货 | 说明 Redis 与 DB 不一致，属于对账范畴，需告警排查 |

核心原则：**Redis 的预扣是"占位"，DB 的落库才是"成交"**。占位失败要还回去，成交失败要能追溯。

**Q4：如何做 Redis 与 DB 的库存对账？**

A：三步：
1. **算差额**：`Redis 剩余库存 + 已售数量` 应该等于 `DB 初始库存`。定期（比如每分钟）跑一次核对。
2. **只告警，不自动修**：发现不一致先告警，人工确认原因。**自动修复是危险的**——如果差异是因为消息还在队列里没消费完，你自动把库存补回去，等消息消费完就变成超卖了。
3. **对账窗口要避开高峰**：活动进行中不做修复，等活动结束后再统一处理（退差、补发、人工介入）。

**Q5：`DECR` 和 `DECRBY` 的区别？库存扣减为什么不用 `GET` + `SET`？**

A：
- `DECR key`：减 1，返回减完之后的值；
- `DECRBY key n`：减 n，返回减完之后的值。
两者都是**单命令原子**的。

不能 `GET` + `SET` 的原因和数据库的"先查再改"一模一样：`GET` 和 `SET` 是两次网络往返，中间任何并发都能插进来。100 个请求读到同一个 `stock = 1`，然后各自 `SET 0`，最后卖了 100 件。

但要注意：**`DECR` 只保证"减"是原子的，不保证"判断"是原子的**。所以正确写法要么是 `DECR` 之后看返回值是否为负、为负再 `INCR` 回来（有短暂负数窗口），要么直接用 Lua 把"判断 + 扣减"包成一个整体。**这也是项目最终选 Lua 而不是裸 `DECR` 的原因。**

**Q6：Lua 脚本太长有什么问题？**

A：因为 Lua 脚本是在 **Redis 的主线程**上执行的，跑脚本的这段时间里，**整个 Redis 实例的所有其他命令都在排队**。

具体后果：
- 脚本跑 10ms，Redis 就有 10ms 什么都干不了。QPS 一万的场景下，这 10ms 能让上千个请求超时；
- 脚本里有循环、有 `KEYS` 全量扫描、有大量字符串拼接，都会把执行时间拉长；
- 脚本里访问了不在 `KEYS[]` 里的 key，Redis Cluster 下直接报错（跨槽）。

所以脚本要**轻**：只做必要的原子判断和读写，不要在里面查数据库、不要做复杂计算、不要写循环。**Lua 是用来守住临界区的，不是用来跑业务的。**
