## 二、Key 设计规范

```
业务:实体:标识:字段        示例
seckill:goods:list:{page}:{size}
seckill:goods:detail:{goodsId}
seckill:goods:stock:{goodsId}
seckill:activity:{activityId}
seckill:order:user:{userId}:{goodsId}
user:token:{token}
captcha:send:{phone}
```

规范要求：

1. 统一冒号分隔，全小写，可读
2. **必须设置 TTL**，且长度加随机抖动（`base + random(0~300s)`）防止同一时刻集体失效
3. 序列化统一（推荐 JSON，可读、跨语言）
4. Key 不要过长（Redis 内存里 key 也占空间）
5. 禁止 `KEYS *`，用 `SCAN`

## 三、三大缓存问题治理

| 问题 | 现象 | 成因 | 方案 |
|---|---|---|---|
| **穿透** | 大量请求打到 DB 且 DB 也没数据 | 查询不存在的 id（恶意攻击） | ① 缓存空值（TTL 短，如 60s）② Bloom 过滤器前置拦截 ③ 参数合法性校验 |
| **击穿** | 单个热点 key 失效瞬间 DB 被打爆 | 热点数据过期 + 高并发重建 | ① 互斥锁（只放一个线程重建）② 逻辑过期（不设物理 TTL，异步更新） |
| **雪崩** | 大量 key 同时失效，DB 崩 | TTL 设置一致 / Redis 宕机 | ① TTL 随机化 ② 多级缓存 ③ 限流降级 ④ Redis 高可用（哨兵/集群） |

### 缓存一致性（Cache Aside）

推荐流程：

```
写：更新 DB → 删除缓存（而非更新缓存）
读：读缓存 → 命中返回 → 未命中读 DB → 写回缓存
```

> 高一致要求场景可再叠加"**延迟双删**"（更新 DB 后删一次，延迟 N ms 再删一次），
> 或订阅 MySQL binlog（Canal）异步失效缓存。
> 秒杀场景库存不走缓存，缓存只用于**商品信息等读多写少、允许短暂不一致**的数据。

### Bloom 过滤器要点

- 优点：内存占用极小、O(k) 查询
- 缺点：**有误判（假阳性），无漏判**；**不支持删除元素**
- 使用：活动开始前把全部合法商品 id 灌入 Bloom，请求先过 Bloom 再查缓存/DB

## 四、多级缓存架构

```
请求 ──► Caffeine（进程内，纳秒级） ──► Redis（毫秒级） ──► MySQL
          热点数据、TTL 极短             全量缓存            兜底
```

| 层级 | 优点 | 挑战 |
|---|---|---|
| Caffeine | 无网络开销，极快 | 多实例数据不一致；需短 TTL 或 MQ 广播失效 |
| Redis | 共享、容量大 | 网络 IO、序列化成本 |

> 本地缓存只缓存**变化极少**的数据（如商品基础信息），秒杀库存这类高频变化数据不要放本地。

## 七、常见坑

- 缓存未设 TTL，Redis 内存持续增长最终 OOM
- 序列化用 JDK 序列化，内容不可读且体积大
- 缓存了"库存"这类高频变更数据，导致超卖或看到脏数据
- 更新 DB 后"更新缓存"而不是"删除缓存"，并发下写覆盖
- Bloom 过滤器未考虑商品新增，新商品永远查不到
- 本地缓存 Caffeine 未设上限（`maximumSize`），内存泄漏

## 八、面试追问

### 8.0 当时到底卡在哪

**卡点一：详情页 QPS 死活上不去，数据库先跪下。**

商品详情接口是读接口，每次请求都查一遍 `t_seckill_goods` 再查 `t_goods`。压测到 200 QPS 时，HikariCP 活跃连接数直接顶满 50，后续请求全在 `connection-timeout` 上排队。

**卡点二：压测脚本里混了一批不存在的 id。**

JMeter 参数化时随机生成了一批 `goodsId`，其中有一部分库里根本没有。这些请求在 Redis 里查不到、在 MySQL 里也查不到，于是**每一次都老老实实穿透到数据库**。明明是"查不到"的请求，却比"查得到"的请求更费资源。

**卡点三：缓存整点集体过期，数据库被打穿。**

预热时用的是固定 TTL（比如统一 30 分钟），结果一批 key 在同一秒过期。那一瞬间所有请求同时回源，数据库像被人从背后推了一把，RT 从 20ms 飙到 2 秒。

**卡点四：Bloom 过滤器重建后，明明存在的商品查不到了。**

为了重建布隆过滤器，我按单个活动做 `delete()` 再逐个灌数据。中间那几秒里，查询会返回"不存在"——**假阴性**。布隆过滤器只允许假阳性（说存在其实不存在），绝不允许假阴性（说不存在其实存在），因为前者只是多查一次库，后者是直接告诉用户"商品没了"。

### 8.1 为什么最后引入了这些技术

**Redis 缓存**，引入它是为了：

- 不是把数据多存一份，而是把慢的挡在门外；
- 不是让数据库变强，而是让数据库少挨打；
- 不是追求"更快"，而是先追求"别倒"——**先活下来，再谈快不快**。

**布隆过滤器 + 空值缓存**，引入它们是为了：

- 不是防"有"的请求，而是防"没有"的请求；
- 不是让查询更快，而是让无效查询根本到不了数据库；
- 不是替代缓存，而是给缓存补一道**过滤器**：假阳性可以忍，假阴性不能忍。

**Caffeine 本地缓存**，引入它是为了：

- 不是不信任 Redis，而是不想让每一次读都跨一次网络；
- 不是多一层复杂度，而是把最热的那部分数据放到离 CPU 最近的地方；
- 不是替代 L2，而是替 L2 挡掉绝大部分重复访问——**越靠近用户的缓存越便宜，越靠近数据库的缓存越贵**。

**TTL 抖动**，引入它是为了：

- 不是为了"看起来随机"，而是为了打散过期时间；
- 不是为了让缓存更长寿，而是为了让失效更分散；
- 不是治本，但足够便宜——**一个 `+ random(0, 300)` 就能挡掉一次雪崩**。

### 8.2 面试追问（附参考答案）

**Q1：为什么是"删除缓存"而不是"更新缓存"？**

A：三个理由，从轻到重：

1. **更新缓存可能写了个没人要的值**。缓存里 90% 的数据可能永远不会被读第二次，为了那次"可能"的读去写一次缓存，是纯粹的浪费。
2. **并发下更新会互相覆盖**。两个线程分别更新数据库和缓存，执行顺序交错时，缓存里可能留下旧值（经典的"并发更新导致脏数据"）。
3. **删除是幂等的，更新不是**。删除失败重试一次即可；更新失败重试可能把新值又改回旧值。

标准做法是**先更新数据库，再删除缓存**（Cache Aside）。极端并发下仍有窗口，但配合"延迟双删"或订阅 binlog（Canal）可以把窗口压到可接受范围。

**Q2：缓存穿透、击穿、雪崩的区别？各用什么方案？**

A：三个问题长得像，病因完全不同：

| 问题 | 病因 | 现象 | 方案 |
|---|---|---|---|
| **穿透** | 查的数据**根本不存在** | 每次请求都打到 DB | 空值缓存（短 TTL）+ 布隆过滤器 |
| **击穿** | **某一个热点 key** 过期 | 大量请求同时回源同一个 key | 互斥锁重建 / 逻辑过期 / 热点永不过期 |
| **雪崩** | **大量 key 同时失效** 或 Redis 整体宕机 | 数据库瞬间被打穿 | TTL 随机抖动 + 多级缓存 + 熔断降级 |

一句话记：**穿透是"查不存在的"，击穿是"一个热点没了"，雪崩是"一片同时没了"。**

**Q3：Bloom 过滤器为什么不能删除元素？误判怎么办？**

A：布隆过滤器本质是**一组位数组 + 多个哈希函数**。一个元素会把自己映射到多个位上置 1；删的时候你没法知道"这些位是不是别的元素也用过"，贸然清 0 会让别的元素"消失"——从假阳性变成假阴性，这是绝对不能接受的错误。

三个应对方式：
- **不删，只重建**：定期全量重建，用双写切换（新过滤器建好后原子替换）；
- **计数布隆过滤器**：每个位改成计数器，支持删除但内存翻倍；
- **换数据结构**：数据量不大直接用 Set，或者用 Cuckoo Filter。

误判（假阳性）本身是设计内的：它只会让一次本该被拦截的请求落到数据库，多查一次而已。**所以布隆过滤器只能放在缓存前面当"筛子"，不能当"答案"。**

另外，重建时必须**一次灌全量**，绝不能按单个活动 `delete()` 后逐个灌——中间那段空窗期会产生假阴性。

**Q4：多级缓存如何保证一致性？**

A：先承认一件事：**多级缓存做不到强一致，只能做到"最终一致 + 窗口足够小"**。

工程上的三板斧：
1. **TTL 兜底**：本地缓存给一个很短的过期时间（项目里 Caffeine 是 `expireAfterWrite(30s)`），即使不一致，最多错 30 秒。
2. **写时删两层**：更新数据库后，同时删 Redis 和本地缓存。本地缓存可以靠广播（Redis Pub/Sub / MQ）通知各实例清理。
3. **热点数据特殊处理**：允许短暂不一致，但要有版本号或时间戳，读到旧版本时主动回源。

关键认知：**一致性不是一个开关，是一个成本**。要求越强，付出的延迟和复杂度越高。秒杀的商品详情允许"30 秒内看到旧库存"，但订单和库存不允许——所以前者用缓存，后者走 Lua 原子操作。

**Q5：Redis 挂了怎么办？降级策略是什么？**

A：分三层回答：

1. **挡**：本地缓存（Caffeine）还在，热点数据能顶一会儿，至少不让所有请求瞬间压到 DB。
2. **限**：接口层限流 + 熔断（Sentinel），把流量削到数据库能承受的量级，宁可拒绝一部分请求，也不让整个系统雪崩。
3. **兜**：非核心功能直接降级（比如"猜你喜欢"返回空列表），核心功能返回友好提示（"当前人数过多，请稍后再试"），而不是抛 500。

要注意的是：**秒杀下单链路强依赖 Redis，Redis 挂了秒杀就应该停止**，不能降级成"直接查数据库扣库存"——那不是降级，那是自杀。降级的前提是"降级后的路径比原来更安全"，不是"换条路继续冲"。

**Q6：为什么秒杀的库存不能直接放普通缓存里减？**

A：因为"读出来 → 减一 → 写回去"是三步，和数据库的"先查再改"犯的是同一个错。

```java
// ❌ 看起来用了 Redis，其实把超卖原封不动搬了过去
Integer stock = redis.get(key);
if (stock > 0) {
    redis.set(key, stock - 1);
}
```

并发下 100 个请求可能都读到 `stock = 1`，然后各自写回 0，最后卖出 100 件。

正确做法有两条路：
- **`DECR` 原子命令**：Redis 单命令原子，但"判断是否大于 0"和"扣减"仍是两步，得靠 `DECR` 返回负数再补偿；
- **Lua 脚本**：把"读库存 → 判断 → 扣减 → 写用户标记 → 返回结果"全部塞进一次原子执行，这才是项目里 `seckill_pre_deduct_stock.lua` 的做法（第 07 章）。

一句话：**缓存能加速读，但不能自动帮你保证写。原子性得自己造。**
