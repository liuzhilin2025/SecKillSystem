## 二、关键设计点

### 1. Sa-Token Token 持久化到 Redis

- 引入 `sa-token-redis-jackson` 后，Token 与 Session 自动落 Redis，支持多实例共享。
- 配置 `sa-token.timeout`（默认 30 天）、`token-name`、`is-concurrent`、`is-share`。

```yaml
sa-token:
  token-name: satoken
  timeout: 2592000
  active-timeout: -1
  is-concurrent: true
  is-share: false
  token-style: uuid
  is-read-cookie: false      # 前后端分离建议走 Header
```

### 2. 短信验证码：Redis + 异步线程池

| 环节 | 做法 |
|---|---|
| 生成 | 6 位随机数字，存 Redis：`captcha:send:{phone}`，TTL 5 分钟 |
| 发送 | 提交到**自定义异步线程池**（核心线程数小、队列有界、拒绝策略明确），避免阻塞 Tomcat 线程 |
| 校验 | Lua 脚本一次完成"取值 + 比对 + 删除"，保证只能成功一次 |
| 限流 | 同手机号 60s 冷却 + 每日发送上限（如 10 次） |

### 3. Redis Lua 原子校验（核心）

```lua
-- KEYS[1] = captcha:send:{phone}
-- ARGV[1] = 用户输入的验证码
local code = redis.call('GET', KEYS[1])
if not code then return -1 end          -- 已过期
if code ~= ARGV[1] then return 0 end    -- 不匹配
redis.call('DEL', KEYS[1])              -- 匹配则立即删除，防止重复使用
return 1
```

> 为什么必须用 Lua：`GET` + 比对 + `DEL` 三步非原子，并发下会被重放攻击。

### 4. 登录安全加固

- 密码错误次数：`login:fail:{userId}` 计数，超过 5 次锁定 15 分钟（Redis TTL 自动解锁）
- 锁定期间直接返回明确错误码，不查库（避免被用来打库）
- 密码存储用 BCrypt，任何日志不得打印明文密码

### 5. 自定义异步线程池规范

```java
new ThreadPoolExecutor(
    corePoolSize,               // 按 IO 密集场景设置
    maxPoolSize,
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(capacity),  // 必须有界，防止 OOM
    new ThreadFactoryBuilder().setNameFormat("captcha-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略明确，不能默认 Abort
);
```

## 四、验收标准

1. 完整走通：注册 → 发验证码 → 校验注册 → 登录 → 带 Token 访问受保护接口 → 退出 → 旧 Token 401。
2. 用 Apifox 并发发同一验证码 2 次，第 2 次必然失败。
3. 连续 6 次错误密码后账号被锁定，15 分钟后自动恢复。
4. 短信接口压测 100 并发，接口 RT 不因"发送"耗时而被拖慢（异步生效）。

## 五、常见坑

- **不要用 `System.currentTimeMillis()` 简单拼验证码**，要真随机
- 异步线程池队列无界 → 高并发下 OOM
- Redis 存储的验证码没设 TTL → 永久有效
- 忘记 `DEL` 验证码 → 可重放
- Sa-Token 未配置 Redis 时，多实例部署登录态会丢
- 把密码明文/验证码写进日志（安全红线）
- BCrypt 每次加密结果不同（含盐），校验必须用 `matches()` 而非 `equals()`

## 六、面试追问

### 6.0 当时到底卡在哪

**卡点一：一个验证码被用了两次。**

验证码存在 Redis 里，我最初写成三段式：先 `GET` 取出来比对，比对通过再 `DEL` 删掉。单线程测一百遍都没问题，并发一上来就出事了——同一个验证码成功注册了两个账号。

原因很朴素：`GET`、比较、`DEL` 是三条独立的命令。Redis 保证单条命令不被打断，但**不保证三条命令之间没人插队**。两个请求同时读到了同一个验证码，同时判断"匹配"，然后各删各的，谁也没拦住谁。

**卡点二：注册接口被短信接口拖着走。**

校验通过后要发短信，短信走第三方 HTTP，本地实测 200~500ms。同步调用时，注册接口的响应时间从十几毫秒涨到几百毫秒；并发一高，Tomcat 的工作线程全卡在"等短信"上，明明只是发个验证码，整个注册功能先雪崩了。

**卡点三：账号锁定被做成了需要长期维护的持久化数据。**

最初的设计是数据库加 `login_fail_count` 和 `lock_time` 两个字段：每次登录失败要 `UPDATE`，登录成功要清零，还要写一个定时任务扫描过期记录来解锁。一个天生"活 15 分钟就该死"的临时状态，被我做成了要一直照顾的长期负担。

### 6.1 为什么最后引入了这些技术

验证码这一步引入 **Lua 脚本**：

- 不是为了炫技，而是为了让「读、比、删」三件事发生在同一个瞬间；
- 不是为了少写代码，而是为了让并发请求排成一队、一个一个过闸；
- 不是为了更快，而是为了更对——**快可以慢慢优化，错不能商量**。

短信这一步引入 **业务线程池**：

- 不是把慢的变快，而是把慢的挪开；
- 不是让请求消失，而是让请求不再堵住主线程；
- 不是逃避第三方的不确定，而是把不确定关进一个有边界的笼子里（有界队列 + 明确的拒绝策略）。

账号锁定这一步引入 **Redis TTL**：

- 不是多存一份数据，而是把"什么时候过期"交给存储层回答；
- 不是省一次 `UPDATE`，而是让临时状态拥有临时的寿命；
- 不是替代数据库，而是把"会自己消失的东西"，放到"会自动让它消失的地方"。

### 6.2 面试追问（附参考答案）

**Q1：为什么验证码校验必须用 Lua？不用会怎样？**

A：不用 Lua 就是 `GET` → 比较 → `DEL` 三条独立命令，中间有两次可以被并发插队的空档。典型事故是"验证码重放"：两个请求同时读到同一份验证码、同时判定匹配、同时执行删除，验证码被用了两次。

Lua 脚本在 Redis 里是**整体串行执行**的：读取、比较、删除在一次执行里完成，第二个请求进来时 key 已经不存在，直接返回失败。项目里的 `check_and_delete_verify_code.lua` 干的就是这件事。

一句话：**Redis 保证"一条命令不被打断"，Lua 保证"一组命令不被打断"。**

**Q2：Token 存 Redis 与 JWT 各自的优劣？**

A：
- **Redis Token**（Sa-Token 默认）：服务端说了算。退出登录、封号、改权限**立即生效**。代价是每次请求多一次 Redis 查询，并且要维护存储与过期策略。
- **JWT**：无状态，不查存储，天生适合横向扩展。但**签出去就收不回来**——想让它提前失效，只能等过期，或者再维护一张黑名单，绕一圈还是要存储。

秒杀场景选 Redis Token：商品可以抢不到，账号不能踢不掉。

**Q3：短信接口为什么要异步？线程池参数怎么定？**

A：短信是外部 HTTP 调用，RT 几百毫秒且完全不可控。同步调用等于把自己的接口 RT 绑在别人的服务上；对方一慢，你的 Tomcat 工作线程就被占住，线程池耗尽后连"读商品列表"都进不来——这就是最典型的雪崩起点。

线程池三件事：
- **核心线程数**按 `峰值 QPS × 单次耗时` 估算，不拍脑袋；
- **队列必须有界**，无界队列只是把 OOM 推迟，不是解决问题；
- **拒绝策略必须明确**，降级记日志或抛业务异常，绝不能静默丢弃还告诉用户"发送成功"。

项目里 `thread.pool` 配的是 core 2 / max 5 / queue 100，属于保守值，真上量要按上面的公式重算。

**Q4：账号锁定为什么用 Redis TTL 而不是数据库字段？**

A：锁定是**临时状态**，天生带过期时间。
- 用 Redis：写入即带 TTL，到点自动消失，不用定时任务、不用惰性判断、不产生垃圾数据；
- 用数据库：要么加定时任务扫表解锁，要么每次登录都先判断"锁定是否已过期"，还要额外维护清零逻辑。

一句话：**会自己过期的东西，就该交给会自动过期的地方。**

**Q5：如何防止短信轰炸（短信炸弹）？**

A：四道闸，缺一不可：
1. **手机号维度**：60 秒一次 + 每号每日上限（Redis 计数 + TTL，对应 `check_and_increment_verify_code_daily_limit.lua`）；
2. **IP 维度**：同一 IP 单位时间内的发送次数限流；
3. **人机校验前置**：滑块/点选验证码通过后才允许触发发送；
4. **内容模板固定**：禁止用户自定义短信正文，避免被当成免费群发通道。

再补一条软防护：监控发送量突增并告警，异常时临时拉黑号段——**技术手段拦得住脚本，运营手段才拦得住人**。
